# Rubric 05: Two stages, one map: holes in stage 2 on purpose

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to an answer before reading the run, with a reason (for example "it is the UART's address, so it prints", or "it is RAM now, so nothing is listening").
- Afterwards records what the run showed: no `hi`, the load returns `0xa` (the newline, the last byte stored), and the stats show no exit at all for the four accesses.
- Draws the conclusion: a mapped address never stops the guest, so the VMM cannot play a device there; the address must be a stage-2 hole.

## Q1

- It is an IPA: the output of stage 1 and the input of stage 2, the address the guest believes is physical.
- In the `va-alias` run the VMM printed `0xb000000`, not the VA `0xb100000` the guest used (still visible in its base register, `x8`).
- The hardware had already walked the guest's own stage-1 tables before stage 2 failed, so it knew the IPA and recorded its page number (`HPFAR_EL2`); with the page offset, shared with the VA in `FAR_EL2`, that gives the whole IPA, which Hypervisor.framework puts in the exit record. No software read the guest's tables.
- With the MMU off (as in `mmio-poke`) VA and IPA are equal, so that run alone cannot tell them apart; the VA is meaningful only inside the guest's current address space.

## Q2

- States a prediction first; "address-size fault" is a reasonable guess, since the address is too wide.
- Decodes the captured DFSC `0x04` as a translation fault at level 0, not an address-size fault (those are `0x00` to `0x03`).
- Explains it: an IPA outside the input range that the IPA size sets is not looked up at all, so the walk fails before reading any table, and the hardware reports level 0. Compares it with `mmio-poke`'s `0x06`, a level-2 translation fault: there the walk ran and found no entry. Chapter 03's address size fault was different: with the MMU off the guest's address was stage 1's *output*, too wide for the CPU, and it was taken inside the guest.
- Notes that "unmapped" has more than one failure mode, and that the DFSC says how stage 2 failed, never what lives at the address; the VMM classifies the IPA against its own map.

## Q3

- Names shadow page tables: the VMM keeps its own tables that map guest virtual addresses straight to host memory, built from the guest's tables, and write-protects the guest's tables so that every write to them traps.
- States the cost: every guest page-table write becomes a VM exit (thousands a second while a kernel creates processes and maps memory), on top of the work of keeping the shadow copy in step.
- With stage 2 the guest edits its own stage-1 tables freely, with no exits; the VMM touches stage 2 only when the machine itself changes (RAM added, a region mapped or protected).
- Notes what stage 2 costs instead: an access whose translation the CPU has not cached walks both stages, so more memory reads, but no exits.

## Q4

- Stock firmware and kernels (U-Boot's `qemu_arm64` build, EDK2, Linux and FreeBSD configured for QEMU) already know or expect these addresses, so mirroring them lets them boot unmodified.
- Holes and reserved windows are part of the contract too: firmware may probe them, and leaving them where QEMU leaves them keeps our machine's answers comparable with QEMU's.
- A cleaner private layout would mean patching or configuring every guest, and losing QEMU as a reference to compare against when something fails.

## Q5

- "No device here" is a choice the VMM makes for a hole: stop the machine (`fatal`, exit code 3) or answer reads with zero and ignore writes (`log`, the RAZ/WI convention).
- With `log`, the reference's `mmio-poke` printed `mmio-poke: survived`: from inside, the hole now behaves like a device that ignores the guest; only the VMM's warning shows the difference.
- A driver decides whether a device is present by reading it, usually identification registers. All zeros (or all ones on some buses) reads as "nothing here" or "a broken device"; a guest cannot reliably tell the two apart.
- Concludes that the answer for unmapped addresses is part of the machine's definition, which is why the default is to stop loudly rather than let a guest probe silently.
