## Predict

- Commits to a time for each plant before running, with a reason (for example "a self-loop is one mutation away from any seed, so seconds").
- Records the actual results: the missing hop budget found in well under a second (iteration 7 in our run), the three-buffer bug only after minutes (about two minutes and 23 million iterations in ours), or not at all within the limit on another seed.
- Draws the lesson: the time to find a bug depends on how many specific choices the input needs and whether the mutator can make them, not on how serious the bug is.
- Notes that the first plant was caught by an invariant (too many descriptor reads), not by a hang: the byte cap ended the loop first.

## Q1

- The missing `checked_add` (a buffer judged by its two ends) is the worst: the guest controls address and length, and the device then reads or writes a span that crosses a hole between host allocations. That is a host memory read or write outside guest RAM, the escape class.
- The ring-index off-by-one is next: the device writes a used element 8 bytes past the ring, at an address the guest chose for the ring. In our layout that lands in guest RAM (corrupting the guest's own data), but the same bug against a ring placed at the end of RAM writes past it; how bad it is depends on the bounds check underneath.
- The missing hop budget is a denial of service: a worker spins or burns its byte budget; no memory outside the guest is touched.
- Rejects "the loop is worst because it hangs everything": a hang harms availability; an out-of-bounds read or write harms the host's integrity and confidentiality.

## Q2

- Everything the process can do as the user: read files the user can read (`~/.ssh`, the keychain the user unlocks), open sockets, start processes, write to the terminal.
- Names the mechanism per asset: the sandbox (on by default) denies opening files by path, all network operations and process creation; the lowered file-descriptor limit stops hoarding; `RLIMIT_CORE` 0 stops core dumps of guest RAM; `umask 077` keeps outputs at most `0600`; one entitlement only, and it is a permission, not a fence; no secrets in the process.
- Names what stays exposed even in the sandbox: guest RAM, the disk images and output files already open, the hypervisor itself, and the terminal settings through the four allowed `ioctl`s.
- Rejects "they own the Mac": with `--no-sandbox` they own the user account, not root; with the default sandbox, they own little more than the VM's own resources.

## Q3

- A logic bug, resource exhaustion, an infinite loop, TOCTOU on shared guest memory (another vCPU rewriting a descriptor between two reads), or a confused deputy (a path used with the VMM's rights for the wrong purpose).
- Shows a real instance or its guard in the learner's code: the hop budget, the `checked_add` on `addr + len`, the single copy of each descriptor, a byte cap on a sink, the output-path checks.
- Explains why Rust does not help: each is memory safe; the program does exactly what it says, and what it says is wrong.
- Rejects "none, Rust is memory safe".

## Q4

- The input generator and mutators encode the author's model of a ring: chains of one to four buffers, readable before writable, addresses drawn from a short list of edges and specials, one queue at a time, one device.
- Names a concrete blind spot: two descriptors at the same arbitrary address (outside the specials list), a chain through the indirect table longer than the seeds build, two queues of one device sharing memory, a ring that overlaps the descriptor table, an input that only fails on the second use of a queue after a reset.
- Names the bug that could hide there, for example an alias between a writable buffer and the device's own ring.
- Proposes a remedy: a random-byte mode with no structure, coverage guidance (`cargo fuzz`), mutating the mutator's choices, or new seeds taken from real guest traffic.
