## Q1

- U-Boot reports `fdtcontroladdr` / `fdt_blob` near the top of RAM (`0x5e6596e0` in our run with 512 MiB), not `0x4000_0000`: it relocated itself and copied the DTB out of the way of what it will load.
- Our original is still at `0x4000_0000`: `md.l` prints `edfe0dd0`, the big-endian magic `d00dfeed` read as a little-endian word (and `97060000` is `totalsize`, `0x697`).
- Same addresses are not the test; same content is: compare `totalsize` (1687 bytes in both, matching `--dry-run`), and, better, the nodes and properties (`fdt print /` against `dtc` of `--dtb-out`).
- A mismatch in the entry state (`x0` not the DTB) would be a boot-protocol bug in the VMM; a different address with the same content is the firmware's own choice.

## Q2

- The flash is mapped read-and-execute only, so a guest store cannot complete: it is a data abort that exits to the VMM. The fault code varies (DFSC `0x7`, a translation fault, for a page never touched; `0xf`, a permission fault, after a read), probably because stage-2 entries are filled lazily; the VMM classifies by its own memory map, never by the fault code.
- The first two stores are `stp` pairs (ISV = 0): the VMM fetches the instruction from the ROM through the read-only hook, decodes it, checks it against the exit, and sends two 8-byte writes to the flash device; later single stores (ISV = 1) go straight to the device.
- The flash device ignores every write and logs it, rate-limited; the PC advances; U-Boot carries on.
- Real NOR flash is programmed with a command protocol (CFI: unlock, erase a sector, program), not plain stores. Read-write memory accepts any store, so the firmware could overwrite its own image, and a "saved" value vanishes at reset when the VMM reloads the image (the break showed `0xdeadbeef` gone after `reset`).
- `saveenv` fails either way here, because U-Boot found no flash chip (`Flash: 0 Bytes`, no `flash@0` node), so it has no sectors to erase (`not on sector boundary`). The default environment at boot has a different cause: bank 1 reads as zeros, so the stored environment's CRC fails (`bad CRC`). EDK2 is the firmware that would force CFI write emulation.

## Q3

- The exit's IPA is the address the hardware actually faulted on, and the hardware checked stage-1 permissions only for that access; the instruction and the tables are read later.
- Between the fault and our fetch, a second vCPU (its own thread) can rewrite the instruction or the page-table entry; and even one vCPU can disagree with itself, if it changed a descriptor without a `TLBI` and the hardware used the stale TLB entry. Either way the recomputed address may name a different page or device, possibly one the guest kernel made inaccessible.
- The checks: the decoded address must translate to the exit IPA; the direction must match WnR; the access must stay inside the one stage-1 mapping (page or block) that faulted; a pair's second element must translate to exit IPA plus the element size and lie in the same device window; a cache-maintenance/load-store mismatch with `ESR.CM` is refused.
- Any disagreement is refused with an injected synchronous external abort, before any device is touched.
- The break passed both guests because neither changes its tables or code after a fault; only a host test that scripts the disagreement (a `translate` that answers with another page: `0xb001008` against the exit's `0xb000008`) catches it.

## Q4

- A standard interface to start any operating system: UEFI boot services, a loader that finds a bootable program on a disk (`\EFI\BOOT\BOOTAA64.EFI`), so the VMM need not know the kernel's format.
- FreeBSD needs it: its kernel has no documented direct-boot protocol and expects `loader.efi` and its metadata (chapter 22).
- Also acceptable: runtime services (variables, reset, time), a boot menu or prompt, partitioned disks, starting a compressed EFI kernel such as `vmlinuz-virt` that our direct boot refuses.
- Wrong path: "nothing, it is legacy"; other operating systems expect it.

## Q5

- We create and place the DTB (start of RAM, by the QEMU `virt` convention); after that it is guest memory, and the firmware owns what happens to it.
- Firmware may copy it (U-Boot did), fix up `/chosen` or `/memory`, or pass its own copy to the OS through the UEFI configuration table; Linux's EFI stub adds to it again.
- So the VMM must never assume the OS sees our DTB unchanged, and must never read back a DTB from guest memory as if it were trusted: anything the VMM later parses from the guest gets the same hostile-input rules as any other guest data.
- What stays the VMM's job: the DTB must be complete and true, since it is the firmware's only description of the machine.
