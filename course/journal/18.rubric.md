## Q1

- `0x1FFF_FFFF_FFFF_FFFF × 512 = 0x3FFF_FFFF_FFFF_FFFE00`; in 64 bits only `0xFFFF_FFFF_FFFF_FE00` survives (the top bits are lost).
- Read as a signed file offset, that is `-512`, which `pread` refuses with `EINVAL`; but other sectors wrap to small, valid offsets (`2^55` wraps to exactly 0), and `pread` reads them happily. A wrapped offset is valid and wrong.
- The break showed it: with `wrapping_mul`, the request for `2^55` answered OK with sector 0's bytes. For the sector `u64::MAX / 512` the multiply fit (offset `2^64 − 512`), but the end wrapped to 0 and passed the capacity check, so that huge offset reached the test's disk: both `checked_mul` and `checked_add` are needed.
- The defence is in the device: `checked_mul` and `checked_add`, the length a whole number of sectors, `end <= capacity`, and `IOERR` before the file is touched. In Rust with overflow checks on, a plain `*` panics instead: a crash the guest can trigger, which is also a bug.

## Q2

- A bad file offset reaches the image file only: the guest can read or overwrite bytes outside its own disk area, which matters if the file is shared, holds another disk's data, or (with a wrapped offset) is sector 0, which the guest did not ask for. That is data corruption or an information leak, but inside a file the guest already owns.
- A bad buffer address is far worse: an IN request copies disk bytes to an address the guest chose. Without the chain walk's check that the descriptor lies in guest RAM, that is a write into the VMM's own memory, a host compromise. An OUT with a bad address reads host memory into the disk file: a leak of whatever the VMM process holds.
- So the two checks protect different things: the sector check protects the file, the descriptor check protects the VMM process. Both are needed, and only the second can turn a guest bug into control of the host process.
- Wrong path: "the guest can only corrupt its own disk". Nudge: what else can the file offset and the buffer address reach?

## Q3

- `man fsync` on macOS: `fsync` sends the data from the host to the drive, but the drive may keep it in its volatile cache and write it later, out of order; `F_FULLFSYNC` asks the drive to flush that cache too.
- On Linux, `fsync` already asks the device to flush its write cache, so the Linux name promises what macOS calls `F_FULLFSYNC`.
- A guest filesystem uses FLUSH as a durability barrier (ext4's journal commits rely on it), so the honest implementation is `F_FULLFSYNC`. In Rust, `File::sync_all` is that call on Apple targets; we checked the pinned standard library source.
- The cost: milliseconds per flush (about 4.7 ms on the lesson's Mac) against well under a millisecond for `fsync`. Durability is part of the device contract, so we pay it.
- The do-nothing version passes because the host tests use an in-memory disk that only counts `sync` calls (they prove the device asks, not that the backend keeps its promise), and every run, even `kill -9`, leaves the macOS kernel running, so the page cache still writes the data eventually. Only a power cut, which no test here can do, shows the bug.

## Q4

- Refuse with `IOERR`. A dropped write that answers OK makes the guest believe the data is on disk; its filesystem then builds on blocks that do not exist, and the damage appears later, far from the cause. That breaks the same promise FLUSH makes.
- Better still, advertise `VIRTIO_BLK_F_RO`: Linux then marks the disk read-only (`ro=1`) and refuses writes itself, as the `,ro` runs showed with `write rejected`, `Operation not permitted` from `dd` and an unchanged hash.
- Defence in depth: the image is also opened `O_RDONLY`, so even a bug in the device logic cannot write.
- Wrong path: "drop them, it is simpler for the guest". Nudge: what does the guest believe afterwards, and when does it find out?
