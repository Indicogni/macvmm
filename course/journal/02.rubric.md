# Rubric 02: An exception, one level up: your first VM exit

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to one address before running, with a reason (for example "a call continues after itself").
- Afterwards records what the run showed: `pc=0x40000008`, after the `hvc`.

## Q1

- Reads `pc=0x40000008`: the address after the `hvc`, not the `hvc` itself.
- Concludes that nobody in our VMM advanced it: the hardware saved the preferred return address when it took the exception, because an `hvc` is a call, and calls continue after themselves.
- Uses `x0=0x2a` as proof that the first instruction ran before the exit.
- Notes that "add 4 to the PC after every exit" would be wrong here (it would skip the `b .`), and that the opposite holds for faults and for an `smc`, which the level above intercepts before it executes: there the PC stays at the instruction, and the VMM must advance it after an `smc`.

## Q2

- Who called, or rather from which level and in which state: `SPSR_EL1` (the saved mode and flags).
- Where to go back to: `ELR_EL1`.
- Why: `ESR_EL1`, whose exception class says "an `svc`" and whose low bits carry its number.
- For faults only, which address: `FAR_EL1`.
- Where the handler is: the vector table whose base the kernel wrote into `VBAR_EL1`.
- Names honestly the item they missed (commonly the saved mode, or the vector table base).

## Q3

- Zero VM exits: `b .` is a valid, endless program, and nothing in it needs the level above.
- The call to `hv_vcpu_run` never returns, so the thread that made it can do nothing; only something outside that thread can stop it.
- Infers the need for an external stop: a timeout (chapter 03's `--timeout`) or a kick from another thread (`hv_vcpus_exit`, chapter 20).
- Does not claim the guest "crashed": an infinite loop is not an error.

## Q4

- At least four threads, one per vCPU, because each vCPU's state lives with the thread that created it.
- Each thread creates its own vCPU and is the only one that calls `hv_vcpu_run` for it.
- Anything another thread wants from a running vCPU (stop it, read its registers) needs an explicit message to that vCPU's thread, not a function call. A thread pool that hands vCPUs around would not work.

## Q5

- The instruction did not change: the guest's own `ESR_EL2` holds `0x5a000000`, exactly the syndrome our VMM saw for the same `hvc` in the main run (exception class `0x16`), and `ELR_EL2` holds `0x40000008`, the same preferred return address.
- The routing changed: an `hvc` takes the exception to EL2, and with EL2 offered to the guest, the EL2 that receives it is the guest's own (emulated by Hypervisor.framework), so the CPU went to the guest's vector table at `VBAR_EL2 + 0x200`.
- Explains the exit we did see: `VBAR_EL2` is 0 and nothing is mapped at `0x200`, so fetching the handler failed, and that failure (exception class `0x20`, an instruction abort at `pc=0x200`) is what reached our VMM.
- Generalises: what reaches the VMM depends on who owns the level an exception is routed to, not on the instruction.
