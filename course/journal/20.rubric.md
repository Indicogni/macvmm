# Rubric 20: SMP: many vCPUs, many threads

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to one outcome before trying, with a reason.
- Afterwards records what happened: the copy does not compile. The bus is shared between vCPU threads, so a device must be `Sync`, which it is not, and an `Arc` gives no `&mut` access.
- Concludes that in safe Rust a data race on a device becomes a compile error, so the races left to find are logic races, such as two locks taken in opposite orders.

## Q1

- `nproc` is 1; the kernel log says `psci: failed to boot CPU1 (-22)`, Linux's "invalid argument" for the PSCI refusal; the second vCPU's thread existed but never ran (its stats line shows no exits).
- Names the three places: the device tree's `cpu@N` `reg`, which Linux passes to `CPU_ON`; our PSCI table, which maps a target to a vCPU; and the vCPU's own `MPIDR_EL1`, which the guest reads to find out who it is (and which its GIC redistributor reports as its affinity).
- Says which refused: the PSCI table had no row for target 1, so `CPU_ON(1)` was `INVALID_PARAMETERS`.
- Notes the worse variant: if only the register disagrees, `CPU_ON` succeeds, the new CPU believes it is CPU 0, and the guest dies silently. All three must come from one function.
- Wrong answer to watch: "both CPUs run, they just have the same ID". PSCI and the kernel name CPUs by this number, so two CPUs with one name cannot both be addressed.

## Q2

- Another thread calls `hv_vcpus_exit` (a kick); `hv_vcpu_run` returns with the reason `CANCELED`. A kick sent before the vCPU entered the guest is sticky: its next run returns at once.
- The vCPU thread owns its registers. Other threads never touch them; they post what they want (the stop flag, a mailbox, a pending interrupt) and then kick.
- Before resuming: the vCPU thread has looked at what was posted (for a stop, the flag; it is set before the kick, so it cannot be missed), the guest's state is consistent (no half-emulated instruction; a `CANCELED` exit leaves the PC at the next instruction not yet run, so nothing is advanced), and no lock is held across `hv_vcpu_run`.
- A kick does nothing to a thread that is not inside `hv_vcpu_run`, such as one blocked on a mutex.
- Wrong answer to watch: "send a signal to the thread". The thread is inside the framework running the guest; only the framework's call can bring it out cleanly.

## Q3

- Shared: the queue's private state in the VMM (the index of the next available entry to read, the used index we publish, the interrupt status) and the backend (the disk file).
- The critical section begins before reading the guest's available index and ends after publishing the used index and updating the interrupt status, so two notifies cannot take the same request or publish out of order.
- It does not cover the long backend I/O when that can be avoided: one vCPU's notify only marks the queue pending and wakes the worker; the vCPU thread must not hold the device lock across blocking I/O.
- Wrong answer to watch: "lock the whole device on every MMIO access, for the whole request". That serialises every CPU behind the slowest disk read.

## Q4

- The caller chooses the context ID; the VMM delivers it unchanged in `x0` of the new CPU, together with the entry point as its PC.
- That lets the entry code find its per-CPU data (a stack, a structure address) at its first instruction, before it has a stack or the MMU on, with no shared-memory handshake that would itself need ordering.
- It is the same "registers are the API" idea as the SMCCC call itself, and as the device tree address that arrives in `x0` of the boot CPU.
- Wrong answer to watch: "it is the CPU number". The target MPIDR names the CPU; the context is whatever the caller wants the new CPU to know.
