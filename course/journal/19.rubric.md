## Predict

- Commits to one of the three outcomes, with a reason, before reading the reveal.
- Records what the run showed: A's VMM sent 20 frames (1,200 bytes), B's VMM delivered the same 20 frames into B's buffers, and B's guest answered none; A printed `FAILED ping 0/5`.
- Works out the shift: B reads the two leftover header bytes (`num_buffers`, which the driver must write as 0 on transmit) and then the frame, so the destination becomes `00 00 ff ff ff ff` (not a broadcast, not B's MAC), the source `ff ff 02 6d 76 00`, and the EtherType `00 01` instead of `08 06`.
- Concludes "nothing": the frame is not visibly corrupt to anyone; it is addressed to somebody else and discarded silently. Framing is a contract between driver and device even with no network behind it.
- Wrong path: "valid packets, the network sorts it out". The device delivered every frame; the meaning was already wrong.

## Q1

- The numbers from the reference run: `rx_dropped_no_buffer=13` in B's VMM stats and `rx_packets` 0 in B's guest, so none of the 13 frames reached the guest (its own receive counter, the `rx_packets` file it printed, agrees); the device dropped them because no receive buffer was posted while `eth0` was down.
- Only ten warning lines appear because guest warnings are rate-limited (the first ten, then one in many); the counter, not the log, is the count.
- In the broken run nothing was counted and nothing was delivered: the frames sat in B's socket buffer while the RX thread waited, and the VM never exited on its own (only a second SIGTERM ended it), so no stats were printed at all.
- Notes that a drop is a normal outcome for a network and the guest's protocols retry (ARP asked again, and again).

## Q2

- A frame waits only in the host socket's receive buffer (1 MiB) until the RX thread reads it; inside the device it waits nowhere. With no posted buffer, the device drops it and counts it, as a physical NIC with a full ring does.
- Never block: the RX thread holds the device mutex while it delivers. If it waited for a buffer, every other user of that mutex would wait too: the worker's transmit path, and the vCPU when the guest resets the device. The `sample` shows exactly that: `vcpu0` in `VirtioMmio::reset` waiting for the lock, the RX thread in `Net::receive` sleeping while holding it.
- The guest cannot unblock it: the only vCPU that could post a buffer is the one stuck waiting. A device that waits for its guest gives the guest (buggy or hostile) a way to stall the host side, and here it stalled the guest itself.
- Mentions the matching rule on the host side: `recv` and `send` have timeouts, so the RX thread sees its stop flag and the worker is never held for long.
- Wrong path: "block until the guest posts one, so nothing is lost". Ask whose thread blocks, and who could ever wake it.

## Q3

- `unixgram:` uses ordinary Unix datagram sockets: to macOS they are files and file descriptors, protected by owner, mode and directory permissions, so no entitlement and no root are needed.
- What it cannot do: reach the host's real network, the internet or another machine; there is no router, no network address translation and no DHCP server handing out addresses. It reaches only another program on this Mac that writes datagrams to the right path, and the peer check limits that to one path.
- `vmnet.framework` attaches a guest to the host's networks, which needs root or the restricted `com.apple.vm.networking` entitlement; an ad-hoc signed program that claims it is killed at launch. Any reason for the gate (a guest could reach whatever the host can) is marked as inference.
- Containment is a limit on what a program can do after it is compromised. Any macOS process may open network connections without an entitlement, so a hijacked `macvmm` could; the audit rule on `std::net` is a review rule, not a run-time barrier. Containment is chapter 25's sandbox.
- Wrong path: "because the sockets are local". Ask what you lose, and what a compromised process could still do.

## Q4

- Picks one and argues for speed: segmentation offload removes most per-frame work for a bulk TCP transfer (one 64 KiB packet instead of about 45 frames, so far fewer chains, copies and doorbells); checksum offload saves the guest's checksum work; mergeable buffers mostly help receive with large packets.
- Names the new parsing risk for each: checksum offload makes the device trust `csum_start` and `csum_offset` (offsets into the packet that must be bounds-checked against its length before the device writes there); segmentation makes it trust `gso_type`, `gso_size` and `hdr_len` and parse the guest's IP and TCP headers to cut the packet; mergeable buffers make one packet span several chains, so `num_buffers` and a loop over chains need a cap.
- Generalises: every offload buys speed with attack surface, because the device must now parse more fields that a hostile guest writes.
- Wrong path: "no risk, the feature is optional". Ask who writes `csum_start`.
