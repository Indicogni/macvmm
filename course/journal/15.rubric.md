# Rubric 15: Rings and a doorbell: the virtio-mmio transport

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to three numbers before reading the measurements, with a reason for each.
- (a): at least one exit per byte, so thousands for 4 KiB; the measured PL011 rate (about 2.7 exits per byte) gives about 11,000.
- (c): about 3 exits for a lone block (one doorbell, then `InterruptStatus` and `InterruptACK` in the interrupt handler), and well under one per block in bulk: the measured virtio disk read 64 MiB, 16,384 blocks, with 85 exits at its slot, 20 of them doorbells.
- (b): also far below (a), because an NVMe controller keeps the data in RAM too and exits only for doorbells and interrupt handling.
- Rejects "the same, both use rings" with the honest difference: an emulated NVMe controller needs at least a submission doorbell and a completion doorbell per batch unless the guest uses the shadow doorbells NVMe added later for virtual controllers; virtio was designed for virtual machines from the start, so suppressing notifications is in its base ring format, one driver serves every hypervisor, and there are no hardware quirks to copy. Notes that (b) was not measured.

## Q1

- Reads `MagicValue` `0x74726976` ("virt"), `Version` 2 and `DeviceID` 0; every other register reads 0 and writes are ignored.
- DeviceID 0 is the specification's definition of an empty transport, and a driver must ignore it.
- The slot answers because the board has 32 transports at fixed addresses, and a guest that scans them (as `virtio-probe` does) must get a defined answer; an unhandled MMIO access would stop the guest instead. (On QEMU, whose device tree lists all 32, firmware probes every one.)
- The device tree lists only populated slots, so Linux never binds a driver to an empty one. Counts the probe's evidence: `dt lists 0 virtio_mmio nodes`.
- Wrong turn to avoid: "empty slots read all ones, like unmapped memory". The specification defines the value.

## Q2

- Features change what the queues and config space look like (ring format, indirect descriptors, notification suppression), so both sides must agree before any queue is set up.
- The driver chooses a subset of the offered features, but only the device knows whether that combination is one it can serve.
- A driver could accept a bit the device never offered (by mistake, or as an attack); the device must not silently run with it.
- Reading `Status` back after setting `FEATURES_OK` and finding it clear is the refusal, and the driver must give up rather than run half-configured.
- `VIRTIO_F_VERSION_1` is required: without it the driver is a legacy driver, which a version 2 transport does not serve.
- In our transport, the refusal is also how features we never implement stay off even when a hostile driver sets them.

## Q3

- Config space is read in several separate MMIO accesses, and a 64-bit field such as a disk's capacity takes two 32-bit reads.
- The device may change the configuration between those reads (a disk resized), so the driver could combine an old low half with a new high half.
- The driver reads `ConfigGeneration`, then the fields, then `ConfigGeneration` again, and retries if it changed; the capture shows generation 0 before and after the capacity read.
- Names it as a check-then-use race (time of check to time of use) that the specification resolves on the guest's side; the device's part is to change the counter on every configuration change.

## Q4

- Before activation: the ring addresses are set (both halves combined as `high << 32 | low`, never added), each ring is aligned and its whole length, computed with checked arithmetic from the queue size, lies inside one RAM region; the queue size is a power of two within the maximum.
- Check once, at `DRIVER_OK`, before anything uses the rings, and answer a failure with `DEVICE_NEEDS_RESET` and a configuration interrupt, not a panic.
- Freeze the registers afterwards, so the checked addresses cannot be swapped for unchecked ones.
- What still changes: everything *inside* the rings. The guest owns that memory and can rewrite descriptors, lengths and indices at any moment, including while the device reads them, so every value read from a ring must be checked again at use and copied before it is checked (chapter 16).
- Wrong turn to avoid: "store it now and check it at first use". First use may be far from the guilty write, after the state machine has moved on.
