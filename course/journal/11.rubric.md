# Rubric 11: Getting the CPU back: the timer and a bare interrupt

## Predict

- Commits to one option before running, with a reason (for example "the guest must stop to wait, and the timer must reach us").
- Afterwards records what the run showed: `vtimer 10, wfx 10` and `canceled 10`, three timer-related exits per sleep, about 30 in all, so (b); and separates them from the `hvc` exits, which are the guest's printing.
- For 250 Hz, predicts about 750 timer exits per second (three per tick, about 1 ms of host CPU per second at 1.43 µs each) and records what the run showed: three exits per tick, but 250 ticks took about 1.66 s (150 ticks per second, so about 450 exits per second), the mean interval was about 5.1 ms instead of 4, and the host CPU line read 23%.
- Says the guest did not keep good time, and why: each wake-up comes about a millisecond late, and each round loses more than a millisecond re-taking the stale pending IRQ before the kick, which the `exec` time and the `stale` count show; the exits themselves are the cheap part.

## Q1

- Reads both values: about 133,000 ticks (a few milliseconds) with the reference's offset, about 3.58 trillion with offset 0.
- Converts the second with the 24 MHz frequency: about 149,000 seconds, some 41 hours, the host's counter since it booted (it does not count while the Mac sleeps).
- Names the leak: without an offset, the guest learns how long the host has been up, which says something about the host it should not need to know, and the value differs from one VM start to the next.
- A fresh machine's counter starts near zero after power-on; the offset gives the guest exactly that, and the same offset on every vCPU keeps their counters equal.

## Q2

- The VMM never cleared the vtimer mask. Hypervisor.framework masks the vtimer itself at a `VTIMER_ACTIVATED` exit and will not exit for it again until the VMM unmasks it.
- The guest is not at fault: it did re-arm its timer (new compare value, `ENABLE = 1`), and the timer's condition did become true.
- Explains the busy loop: with no VTIMER exit, the line is never raised; the WFI handler finds the deadline already past and wakes at once, the guest runs `WFI` again, and so on, millions of WFI exits at nearly 100% of a core.
- The right moment to unmask is when `CNTV_CTL_EL0` shows the timer no longer asserting (`ENABLE = 0`, `IMASK = 1` or `ISTATUS = 0`), checked before each entry.

## Q3

- The VTIMER exit came at about 102 ms, while the guest spun with IRQs masked: the exit is the timer's, and does not wait for the guest to listen.
- The handler ran only when the guest cleared `PSTATE.I`, about 300 ms after arming, which is why interval 0 read 300 ms.
- Meanwhile the interrupt existed only as state: the timer's `ISTATUS`, the VMM's model of the line, and the IRQ the VMM set pending again before every entry (the `canceled` exits every 1.3 ms are those re-checks). Nothing was lost, because the timer's output is a level.
- States the general rule: an interrupt is pending state that is delivered when unmasked, not a call into the guest.

## Q4

- Everything still works: every interval passed, because `WFI` is allowed to end early, so a guest must always re-check its condition after it.
- The cost is a host core kept busy by an idle guest: about 900,000 WFI exits in one second and about 90% host CPU in the reference's run, against 2% with the sleep.
- Notes that the checkpoint fails it on the host CPU limit, not on correctness: correctness and efficiency are different properties.

## Q5

- With one input, the handler cannot tell sources apart by the IRQ itself; it would have to ask every device in turn whether it was the one (read each status register), which grows with the number of devices.
- Priority needs something that ranks pending sources and presents the most urgent first; routing needs something that knows which CPU each source should reach.
- Concludes that these jobs belong to a device between the sources and the CPUs that records which line is pending, ranks them, routes them and learns when the CPU is done with each one: an interrupt controller (chapter 12). That last signal is also what our bare line lacked, which caused the stale re-takes.
