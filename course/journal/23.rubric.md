# Rubric 23: macOS guests, the high road: Virtualization.framework

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to an outcome before running, with a reason.
- Afterwards records what the run showed: with `console=ttyAMA0`, nothing at all on standard output, yet `VZ guest state: stopped (guest)` and exit 0, so the kernel and `/init` ran and nobody heard. Then, from the second run, that the guest really printed on `hvc0`.
- Explains why: `ttyAMA0` names a PL011, VZ's machine has none, and its serial port is a virtio-console, which Linux calls `hvc0`. Because the command line named a console, Linux enabled only a console of that name; `hvc0` registered but was never switched on. The kernel is identical; the machine is not.
- The tempting wrong answer, "the same PL011", is named and corrected.

## Q1

- `com.apple.security.hypervisor` lets `macvmm` create VMs and run vCPUs itself; *we* define every device, so our device code is what a hostile guest attacks, in our process, which holds one entitlement.
- `com.apple.security.virtualization` lets vz-mac ask VZ for a whole machine; *Apple's* code defines the devices and runs in a separate service process that holds many entitlements, several private (such as `com.apple.private.hypervisor`).
- Compares rather than ranks: we can read, test and patch our code but must get it right ourselves; Apple audits and patches its code, which we can neither read nor fix.
- A weak answer says "VZ is safer, case closed". Ask: who audits each, and who can patch it?

## Q2

- Standard virtio, with a public specification: block, console (`hvc0`), entropy, network, socket, file system, balloon (the `VZVirtio*` classes). In the Linux guest they appear on PCI with vendor `0x1af4`.
- Other public standards that Apple emulates: the USB devices (keyboard, pointing device, mass storage) and the NVM Express (NVMe) disk controller. Apple implemented them, but their specifications are public.
- Apple-specific: graphics (`VZMacGraphicsDeviceConfiguration`), keyboard and trackpad (`VZMacKeyboardConfiguration`, `VZMacTrackpadConfiguration`), and the Mac platform itself (hardware model, machine identifier, auxiliary storage, the boot loader).
- Separates "Apple implemented it" from "Apple defined it": only the second leaves a low-level VMM without a specification.
- A macOS guest's display is paravirtual graphics, not a virtio device: its host half is ParavirtualizedGraphics, a public macOS framework, but the protocol the guest speaks to it is undocumented.
- A weak answer says "all virtio". Ask: how does the guest get a display?

## Q3

- For the low road: control and transparency (every exit and device visible), guests and firmware VZ does not offer (U-Boot, FreeBSD through it), custom or instrumented devices, a different security model, learning, and independence from one vendor's private machine.
- For the high road: VZ is supported, works today, is maintained and patched by Apple, and is the only supported way to run macOS guests.
- The honest conclusion includes "for a macOS guest, mostly you would not take the low road", or says when you would.
- A weak answer says "VZ is limited" without naming one concrete thing your VMM can do that VZ cannot.

## Q4

- Lists pieces beyond the CPU and memory, which Hypervisor.framework already gives you: the boot ROM, the Mac platform identity and auxiliary storage, Apple's configuration and boot-disk devices, the keyboard and trackpad, paravirtual graphics, and installation (personalization tied to Apple's installer).
- Classifies each: most are hard because they are undocumented or private (graphics, identity, boot chain), not because they are complex; PCIe is large but documented.
- Notices that one piece may be blocked by permission rather than by work: something only Apple's privately entitled service can do.
- A weak answer says "the CPU stuff". Ask: which part of the CPU have you not already done?
