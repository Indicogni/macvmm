## Q1

- EC `0x24`, a data abort from the guest; ISV = 1 (bit 24), so the other fields are valid.
- SAS = 2 (bits 23:22): 4 bytes. SRT = 9 (bits 20:16). SF = 0: a `w` register. WnR = 1 (bit 6): a write. DFSC `0x6`: a translation fault, the stage-2 hole.
- The instruction is a 4-byte store from `w9`, `str w9, [x8]`; the base register is not in the syndrome, but `x8=0x000000000c000000` in the dump matches the IPA.
- Confirms it with `insn at pc: 0xb9000109`, which decodes to `str w9, [x8]`.
- Maps the fields to a trace record: `wnr`, `size` and `reg` (and `ipa`).
- Does not claim the VMM fetched or decoded the instruction to get these values: that is the misconception.

## Q2

- To emulate an access the VMM needs its direction, size and register; with ISV = 1 the hardware already decoded them, so we emulate the access, not the instruction.
- Without them: read the PC, translate it through the guest's own page tables (a stage-1 walk, since the PC is a virtual address once the MMU is on), copy the instruction word out of guest memory, decode the whole load/store encoding space (sizes, sign extension, writeback, pairs), then check the decode agrees with the fault.
- Each of those steps reads guest-controlled memory and tables, so each is new attack surface and new bugs; chapter 21 pays that cost when firmware needs it.
- Not "to make it faster": the point is that the alternative is a large, risky piece of code.

## Q3

- The syndrome has one register field (SRT) and one size; a pair moves two registers (and writeback forms also change the base register), so the architecture leaves ISV = 0 and the other fields UNKNOWN.
- The same holds for other instructions the note cannot describe: exclusives, atomics, SIMD and floating-point loads, `DC ZVA`.
- A pair access to a device register is a guest choice that real device drivers avoid (Linux writes its device accessors as single loads and stores); our job is to fail clearly, printing the instruction word, not to guess. The guessing break shows why: no crash, exit code 0, and every result wrong.
- Adding a decoder commits you to the stage-1 walk, every addressing mode, writeback with SP rules, checks that the decode matches the exit, and a decision for each form you refuse. It never ends at `ldp`.

## Q4

- IL is the instruction length: 1 means a 32-bit instruction, 0 a 16-bit one.
- Every AArch64 instruction is 32 bits; a 16-bit instruction exists only in AArch32's T32 (Thumb) state, which our VMM never runs.
- So IL = 0 should never happen; the honest response is to check it and stop the VM with a clear error (or, in a VMM that supported AArch32, advance by 2), never to add 4 blindly.
- Generalises: a value from hardware that we "know" is constant is still an input; checking it is cheap and turns a silent corruption into a visible stop.
