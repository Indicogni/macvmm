## Predict

- Commits to an answer before running, with a reason (for example "the UART registers are the same, so neither", or "Linux checks clocks").
- Afterwards records what the runs showed: Linux never binds `ttyAMA0` and prints only `Warning: unable to open an initial console.`, while its early console carries on; FreeBSD boots to `login:` unchanged.
- Notices that "complains" was the wrong word: Linux did not print an error about the clock at all. The symptom is an absence (no console line, no init output), which is harder to spot than an error.
- Explains the difference by binding rules: Linux's AMBA bus needs a clock named `apb_pclk` before it probes a PrimeCell; FreeBSD's PL011 driver binds by `compatible` alone.

## Q1

- Lists real differences from the comparison: QEMU has nodes we lack (`flash@0`, `pcie@10000000`, `fw-cfg@9020000`, `platform-bus@c000000`, `pmu`, `aliases`, `pl061` and `gpio-keys`, 31 more virtio-mmio slots, and none that QEMU lacks), virtio-mmio interrupts declared edge (`1`) where ours say level-high (`4`), a redistributor region sized for 123 CPUs where ours is sized for the two we create, and `arm,cortex-a57` against our `arm,arm-v8`.
- For each chosen difference, names a plausible symptom: no `aliases` could change how a guest names its serial port; a wrong trigger type could lose or repeat interrupts; no `flash@0` means firmware or an OS finds no flash to store variables; a GIC region size that disagrees with what the guest probes could make it touch memory that is not there.
- Picks differences that could plausibly matter to a guest other than FreeBSD 15.1 and Linux (for example an OS that finds its console through `aliases`, or one that writes UEFI variables to `flash@0`), and says how it would test that: boot that guest and compare the log, not reason from the two that booted.
- Keeps the evidence straight: FreeBSD 15.1 and Linux booted with all of these differences, so none of them mattered *to those guests*; one that matters to another guest would need its own run.
- Distinguishes "different from QEMU" from "wrong": ours declares level because our device drives a level line.

## Q2

- Asks first what FreeBSD expected and where it read it: a feature bit the device offered (`VIRTIO_BLK_F_SIZE_MAX`) and the value in the config space.
- Reads the primary sources: the virtio 1.2 specification (the feature is optional for a device, and a driver may refuse a device it cannot drive), FreeBSD's `vtblk_attach` (it refuses a `size_max` below its maximum transfer, with `EOPNOTSUPP`, error 45), and QEMU's device (which does not offer the feature).
- Concludes with reasons: neither side broke a rule, but our device made a promise it never needed, the reference machine does not make it, and dropping it costs nothing (the device copies in 64 KiB pieces anyway). So the machine changes.
- Names the decision rule: if QEMU `virt` presents it differently and both guests work there, ours is the odd one out; if the specification says optional and a guest refuses it, avoid it unless it buys something.
- Rejects "FreeBSD is less mature" or "Linux works, so the machine is right" as conclusions without evidence.

## Q3

- A DTB only *describes* hardware: addresses, interrupts, compatible strings. UEFI provides *services*: code the operating system can call.
- Boot services seen: block I/O on the disk and its partitions (the loader read the kernel through U-Boot's virtio driver, `lsefi` shows `block io`), a text console (`simple text output`), device paths, loading and starting an EFI program from a file system.
- Runtime services seen: `ResetSystem`, which FreeBSD's power-off used (the trace's `PSCI_SYSTEM_OFF` from U-Boot's code near the top of RAM); also variables and time, as the `uefi` primer lists.
- Also: a standard way to hand over tables (the DTB arrives through the configuration table, `Using DTB provided by EFI`), and a standard place to find the boot program (`\EFI\BOOT\BOOTAA64.EFI`), so one disk image boots on any UEFI machine.

## Q4

- A list of tests decided before looking, each tied to a part of the machine: root file system mounted (disk); a write that survives a reboot (disk durability); `login:` answered and a command run (UART in both directions, interrupts); both CPUs online (SMP, PSCI `CPU_ON`); the date right (RTC); timers working (a `sleep` that takes as long as it should); clean power-off with exit code 0 (PSCI through UEFI).
- Notes what the reference's test checks and what it does not: it logs in, runs `uname -sr`, powers off, forbids known error lines, but does not write a file and reboot, or run a network.
- Argues that the banner proves only that the CPU, memory and the console's output path worked up to that line.
- Optionally: a soak or repeated run to catch timing-dependent failures, and the same checks with a different CPU count.
