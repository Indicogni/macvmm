# Rubric 04: Guest memory: the only safe access is a copy

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to one outcome before running, with a reason (for example "the Mac's pages are 16 KiB").
- Afterwards records what the run showed: `hv_vm_map: HV_BAD_ARGUMENT`, an error, not a silent rounding.
- Notes that the guest's own page tables may still use 4 KiB pages: two translations, two owners, two page sizes.

## Q1

- The true sum is `0x1_0000_0000_0000_0004`, which needs 65 bits; in 64-bit wrapping arithmetic it is `0x4`.
- Both halves of the check pass: `addr` is above the base, and `0x4` is below the end.
- The offset `addr - base` is `0xFFFF_FFFF_BFFF_FFFC`; added to the host base it wraps to `host_base - 0x4000_0004`, about 1 GiB below the start of the RAM allocation: host memory the guest was never given.
- Avoids the wrong answer "Rust panics on overflow, so it is safe": with overflow checks off (Rust's release default) it wraps, and with them on it panics, which lets a guest crash the VMM. Only `checked_add` turns it into an ordinary refusal.

## Q2

- No: a `&[u8]` promises the compiler that nobody changes the bytes while the reference lives, and the guest, another vCPU or a device thread can.
- The compiler acts on the promise: the slice version loads the byte once and has no loop at all, while the volatile version loads on every try.
- Notices that the raw-pointer version with an ordinary load is hoisted too: what the optimiser relies on is "an ordinary read means nobody else writes" (otherwise there would be a data race); only volatile or atomic accesses forbid that. The slice adds the stronger promise that the bytes stay unchanged for the reference's whole lifetime.
- The contract offers copies only: `read` and `write` into and out of buffers the VMM owns, `check_range`, the little-endian helpers and `read_obj`. The VMM validates its own copy, never guest memory.
- `copy_nonoverlapping` is an ordinary copy: it assumes nobody else writes, so the compiler may re-read the source later instead of using the copy. Volatile element copies read each guest element exactly once, at its size for aligned `u8` and `u64` on arm64.
- Strong answers note the limit of the argument: Rust's documentation says volatile does not make a race on ordinary Rust memory defined; guest RAM qualifies because it comes from `hv_vm_allocate`, outside any Rust allocation, no reference into it exists, and the guest writing it is an agent outside the program.
- Says what volatile does not give: no atomicity across elements, no ordering with other threads or the guest.

## Q3

- Not today: there is one vCPU, and it is stopped while the VMM handles its exit.
- It becomes possible as soon as something runs at the same time as the guest: a device worker thread reading a request while the guest keeps running (chapter 16), or a second vCPU writing memory while the first one's exit is handled (chapter 20).
- Names the danger: a value checked at one moment may differ at the next, so "check, then use the original" fails; reading once into a copy and checking the copy does not.

## Q4

- Apple silicon Macs use 16 KiB memory pages, and HVF's stage-2 table uses the same page size by default, so mappings and their permissions come in 16 KiB pieces. (Since macOS 26, `hv_vm_config_set_ipa_granule` can opt a VM into a 4 KiB stage-2 granule; macvmm keeps the default.)
- With the default granule, all three must be 16 KiB multiples: the host address, the guest address (IPA) and the size. The Try it showed each misalignment alone is refused.
- The guest's own page tables are a separate translation and may use 4 KiB pages.
- Expects it to return wherever memory is mapped: the machine's memory layout (chapter 05), the flash for firmware (chapter 21), and tracking which pages changed for snapshots (chapter 26).

## Q5

- Lists several resources other than RAM: CPU time (an endless loop, or a flood of exits), log and console output (a guest printing without end), files and file descriptors, threads, and request queues or buffers sized from guest-supplied numbers.
- Notices the common pattern: any size, count or rate the guest controls needs a cap the VMM chooses.
- Optionally connects it to this chapter's memory-hash call, which caps the length it hashes and checks for a stop request as it goes, so one call cannot hold a vCPU thread for long.
