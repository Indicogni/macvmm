## Q1

- Wrapping subtraction: `0x0002 - 0xFFFE` in `u16` is 4 (as if `0x10002 - 0xFFFE`). Not "negative, so none".
- The slots are the counters modulo 8: 6, 7, 0, 1.
- A jump of 65535 (or anything above the queue size) is impossible for an honest driver, because only N slots exist. The device refuses it (an error, the queue marked broken, `DEVICE_NEEDS_RESET`), instead of looping 65535 times or re-serving stale slots.

## Q2

- If the shared index wrapped at the queue size, "the ring is full" and "the ring is empty" would look the same (both sides at the same slot); free-running counters tell them apart by their difference (0 or N), with no wasted slot and no extra shared flag.
- Each side owns one counter: the driver writes `avail.idx`, the device keeps its own private `next_avail` (and writes `used.idx`, never reading it back), so there is a single writer per location and no lock.
- Wrapping subtraction of two counters gives the number of pending entries directly, at every point of the wrap, because 65536 is a multiple of every legal queue size (a power of two).
- Not "to save memory".

## Q3

- Only checks made on the copy we then use still hold. `next < N`, the hop budget, `len > 0`, `addr + len` without overflow and inside RAM, and the direction flag are all checked on the local `Descriptor` that `read_obj` copied once, and the device uses that copy, so a later rewrite of guest memory cannot reach it.
- The guest's rewrite still has effects we accept: it changes what the next walk sees, and the *contents* of the buffers can still change while we copy them, so devices copy or parse buffer data once too.
- The ring indices are also guest memory: `avail.idx` is loaded once per pop, and `used.idx` is never read back.
- Breakage 3 was caught only by the tests that change memory during the walk (the mutation hook and the racing writer); the 62 hostile-ring tests passed because their memory never changes after it is set up, so a re-read returns the same value. Validation that is only tested on still memory does not test for double fetches.

## Q4

- The release store of `used.idx` orders every earlier write, the used element `{id, len}` and the buffer data, before the new index. It pairs with the driver's `virtio_rmb()` after it loads `used.idx`, so a driver that sees the new index sees the element and data.
- The `SeqCst` fence orders our `used.idx` store before our later load of `avail.flags`: a store followed by a load, which release and acquire do not order. It pairs with the driver's `virtio_mb()` between clearing `NO_INTERRUPT` and re-reading `used.idx`; without it both sides can read stale values, and the result is a lost wakeup: a finished request nobody is told about, and a hung guest.
- (The acquire load of `avail.idx` pairs with the driver's `virtio_wmb()` before it bumps `avail.idx`.)
- x86's ordering (TSO) never reorders two stores, so a missing release hides there completely. The store-then-load reordering does exist on x86, but needs a narrow timing window.
- On this Mac, the host tests run both sides in one thread on `VecMemory`, so no reordering can show. Linux still booted and read 1 MiB through a queue with the release removed. Only the access log (a structural check) caught it. Absence of failure is not evidence; the rule is.
- Atomic and ordered are different properties: a 16-bit store is already indivisible; what the release adds is order.

## Q5

- Our device refuses the chain before it touches any buffer: `into_validated` sees a device-readable descriptor after a device-writable one and returns `ReadableAfterWritable`; the queue is marked broken and the device goes to `DEVICE_NEEDS_RESET`. No status byte is written anywhere.
- The direction flags are guest-controlled data, checked against the protocol on the copy, like every other field.
- A naive device trusts positions instead of flags: it parses a "header" the guest marked writable, reads "data" from a buffer it then treats as a destination, and writes its status byte into a buffer the guest marked device-readable, which may hold data the guest did not expect to change (for example a page shared with something else).
- The answer belongs at the chain level, once, for every device, not repeated (and forgotten) in each device model.
