## Q1

- Both reads show TXFE = 1, BUSY = 0, RXFE = 1 (`0x90`, the reset value): our transmit "completes" the moment `DR` is written, so nothing is ever in flight.
- A real UART shifts the byte out bit by bit at the baud rate: right after the write it would show BUSY = 1 (and TXFE = 0 while the byte sits in the FIFO), and only later idle again.
- A *consistent* lie is fine because a driver polls TXFF, TXFE or BUSY and only waits while they say "not yet"; a device that is always ready is a fast UART, which every driver must accept.
- An *inconsistent* lie breaks drivers: TXFF = 1 forever (the break in this chapter) means the guest never sends; RXFE = 0 with an empty FIFO makes the guest read zeros forever.
- Notes that reading `FR` has no side effect, so reading it twice gives the same answer; that is a property of `FR`, not of registers in general.

## Q2

- Arrival: the byte enters the receive FIFO; `FR.RXFE` clears; `RIS` gains the receive bit (`0x10`, and in our model the timeout bit `0x40`); `MIS = RIS & IMSC`.
- The mask: with `IMSC` = 0 the device still remembers (`RIS` set) but does not say so (`MIS` = 0, line low); setting `IMSC` bit 4 raises the line at once.
- `ICR` is write-1-to-clear; it clears a latched bit such as transmit. In our model it cannot hide a receive condition that still holds: while the FIFO has data, the receive bits of `RIS` stay set (a real PL011 lets `ICR` clear them; the spec hunt asks how).
- Reading `DR` pops the FIFO: that is the side-effecting read. When the FIFO empties, `RXFE` sets again, the receive bits of `RIS` fall and the line drops. Reading `DR` on an empty FIFO returns 0.
- Reading `FR`, `RIS` and `MIS` changes nothing; only `DR` has a read side effect here (the identification registers are constants).
- Wrong answer to avoid: "store the last value written and return it". Reading `DR` twice shows why.

## Q3

- The lock protects the device's own state (the FIFO, the status and mask bits) from torn updates: one register access, or one input push, is applied whole.
- It does not order whole messages: two vCPUs printing lines interleave byte by byte. Only the guest kernel knows what a message is, so its own console lock must keep lines together.
- It must never be held while blocking on host I/O: every vCPU that touches the UART (and the stdin thread delivering input) would wait behind a stalled terminal, and a stop request could not reach a vCPU blocked outside `hv_vcpu_run`. That is why output goes to a queue drained by another thread, and why the input push never waits.
- Names the lock order: the device's lock first, then `SerialInput`'s (taken inside `refill`), and the push hook runs with the queue unlocked, so no thread ever takes them in the opposite order.
