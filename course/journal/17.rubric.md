## Predict

- Commits to "bytes" or "buffers", and a number, before running.
- Records what the trace showed: 16,387 doorbells for 1,048,576 bytes, so one doorbell per 64-byte buffer (1,048,576 / 64 = 16,384; a baseline run with `count=0` rang twice, from the kernel's own reads, and the count varies by one or two from run to run).
- Explains that the count follows *buffers posted*: each request is one chain, one doorbell, and (for this driver) one interrupt. Here buffers and bytes grow together only because Linux's driver always posts the same small buffer; the 4 KiB console write (two doorbells, 2,048 bytes each) and the `console-tx` run (one doorbell per 7-byte line) show the same rule with different buffer sizes.
- Notes that the device could not change this on its own: the driver decides how big its buffers are and how often it rings.
- Wrong path: "virtio is fast, so 1 MiB must be cheap". It cost about 51,700 exits and 0.39 s, because 64-byte buffers make virtio nearly as chatty as a register per word.

## Q1

- The numbers: PL011 about 8,194 extra exits for 4,096 bytes (about two per byte: a read of the flag register to see whether the transmit queue has room, then the write of the data register); `/dev/hvc0` 4 extra exits (two doorbells, because the tty layer hands the driver 2,048 bytes at a time, and one interrupt, read and acknowledged). Ratio about 2,000.
- In time, at the learner's own chapter 03 cost per exit (the reference measured 1.43 microseconds): about 11.7 ms of exits for the PL011, about 6 microseconds for the console.
- One `QueueNotify` buys a whole buffer, of any size the driver chose, for one exit; the bytes themselves move by memory copies that cost no exit.
- The misconception named: the console is not faster because its code is faster (it does more work per call: a chain walk, validation, a copy). It is faster because it needs far fewer exits.
- Bonus: the same console cost 9,363 doorbells for 64 KiB when `head` passed on one 7-byte line per `write`; the cost follows the guest's buffers. Chapter 14's 178,073 extra exits for the same 64 KiB through the PL011 are still about 7 times more.

## Q2

- The spec lets the device fill fewer bytes than the buffer holds ("one or more random bytes"); it must never write past the writable descriptors and never write into readable ones.
- `used.len` is the number of bytes the device actually wrote (the return value of `write_writable`), never the buffer's size.
- `getentropy` gives at most 256 bytes per call, so the fill is a loop of 256-byte chunks into a fresh, zeroed bounce buffer.
- The reference caps one request at 64 KiB and treats a larger writable total as a driver error (`TooLarge`, so `DEVICE_NEEDS_RESET`), so every device has one limit enforced in the shared validator before any byte moves; another defensible design fills 64 KiB and reports 65,536. Either way the report matches what was written.
- If the device reports more than it wrote, the driver believes the extra bytes are random: a driver that mixes readable and writable descriptors takes its own readable bytes (or old data) as entropy, and nothing fails visibly. Linux's driver trusts `len` as the valid bytes of its 64-byte buffer, so a `len` above 64 would make it copy past that buffer. The deliberate break shows Linux reading 1 MiB "ok" while the contract tests fail.

## Q3

- A request/response chain works when the guest starts the exchange (rng: post an empty buffer, get it back filled). Console input starts on the host, at any moment, so there must already be somewhere to put it; output exists only when the guest has text. The two directions have different owners of the moment, so they get separate queues: device-writable buffers posted in advance for receive, device-readable buffers posted on demand for transmit.
- The device cannot allocate guest memory; it can only write into buffers the driver handed over. So for receive, the guest must post empty buffers in advance, and the device holds them until host input exists (it pops nothing while the input is empty).
- A UART needs no queue because it moves one byte per register access in either direction: the "buffer" is the data register, and each byte is its own exit.
- Wrong path: "one queue can be bidirectional". Nudge: who owns a buffer while it sits in the ring, and who may write it?

## Q4

- Whatever the choice, the device must not hang, must not write anything, and must not report bytes it did not write.
- One reading: fill nothing and return the chain with `len = 0`; the driver must not use bytes beyond `len`, so this is safe, and the guest can post a real buffer next.
- The other reading, which the reference takes: the spec says the device places "one or more" random bytes, which a zero-length buffer makes impossible, so the chain is a driver error; the chain walker refuses zero-length descriptors (`ZeroLength` in the `hostile-vq` run) and the device goes to `DEVICE_NEEDS_RESET` until the driver resets it.
- A strong answer weighs them: lenient keeps a sloppy driver working but returns an empty buffer that a driver might re-post forever (bounded by the per-batch budget); strict turns a protocol violation into a visible, recoverable state.
- Names the evidence that would settle it: the spec's driver requirements for descriptors, and what Linux's driver ever sends (never a zero-length buffer).
