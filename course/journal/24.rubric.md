# Rubric 24: macOS guests, the low road: vmapple and AVPBooter (capstone, STRETCH)

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to a direction (more, fewer, the same) or to "unknown" with a stated surprise, before running.
- Afterwards records what the run showed: 16 distinct addresses against 14, 63 accesses per boot against 34, bdif reached for the first time, then `PSCI_VERSION` and `SYSTEM_RESET`, repeated until the reset-storm guard stopped the run (exit code 3). Your numbers may differ with another AVPBooter.
- Says how the run ended, not only how far it got: no stall at all, but a reset storm.
- Does not call the all-ones run "better": it is a different, equally guessed machine.

## Q1

- Names the access by what may be published: its layout row (cfg), its size and direction, and its place in the order; not the value written.
- Three distinct hypotheses about the register (for example a status or "ready" bit, a version or identification field, a field the ROM only writes and never checks), each tied to QEMU's public field list where possible.
- For each, an experiment that changes one variable: return a distinct value per hypothesis (0, all ones, a plausible version such as 2) and see whether the *next* access or the stop changes.
- Starts every hypothesis as inferred or unknown, and moves one to observed only with a run that shows it.
- Wrong turn to avoid: "guess the right value and implement it". How would you know it was right?
- The pvpanic Try it: per QEMU's `docs/specs/pvpanic.rst`, a guest writes there to tell the host it has panicked; "AVPBooter gave up" stays inferred at best, since we see a write but interpret no value. An experiment that moves it changes one variable and watches whether the pvpanic write appears, disappears or moves in the order.

## Q2

- Waiting for a device we lack looks like repeated exits near the end: the same address read again and again, with high exec time.
- Waiting for an interrupt looks like WFI time with little exec time and no exits (in-kernel WFI).
- No progress without waiting looks like neither: no exits at all near the end while exec time is close to the wall time (the zero run: 34 accesses in the first 0.5 ms, then only the cancel at 20 s, `exec 19.0 s`, `wfi 0.000 s`).
- Uses the numbers, not the feeling: "both just look like a hang" is the answer the counts disprove.
- Keeps the cause of the loop unknown, because finding it would mean reading the code.

## Q3

- Running the ROM on your own Mac is use under the licence; every exit shows an address and a value whether you want it or not.
- The line our project draws: load the ROM in place from the system path, never write it to a file, log only accesses to devices that do not exist (capped), never disassemble or decompile, never publish per-access logs, written values or guesses about the code.
- Redistribution is about what leaves your machine: the repository holds no copy, which the hash check shows, and learners use the copy already on their Mac.
- A case near the edge, declined: publishing a full access log, reading instructions at a trapping PC to "understand" a loop, trying to recover the AES engine's built-in keys, or copying the ROM into a test fixture.
- Says the licence is the source and the answer is not legal advice.
- Wrong turn to avoid: "it is on my machine, so anything goes". What does your repository contain?

## Q4

- Criteria written before the work, each observable in a trace or a log: for example no new layout row or new address reached after N experiments; repeated stops at a device that QEMU documents only as unknown fields; a dependency on something only Apple has (the private CPU mode, `HV_DENIED`; the signing service; built-in keys); a fixed time budget with no change in the trace.
- Distinguishes "hard because complex" (PCI Express, documented) from "hard because undocumented or reserved" (graphics bridge, AES keys, the CPU mode).
- Treats an honest "not feasible, and here is the evidence" report as an engineering result, not a failure.
- Wrong turn to avoid: "never stop". What does continuing cost, and what would you learn?
