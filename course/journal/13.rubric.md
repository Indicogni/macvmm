## Q1

- `image_size` is the kernel's promise about memory, not about the file: from its first byte, it will use that many bytes, including its BSS and early page tables, which a kernel build need not store in the file.
- In this Alpine build the file happens to be padded with zeros up to `image_size` (its last non-zero byte is about 9 MiB before the end), so the file length and `image_size` agree only by construction; a loader that used the file length would be right here and wrong for an unpadded Image.
- The plan's numbers: the kernel owns `0x4020_0000..0x424a_0000`; the initramfs starts at `0x4260_0000`; the gap `0x424a_0000..0x4260_0000` (1.375 MiB) is our 2 MiB rounding, not something the protocol asks for.
- Anything placed by "where the file ends" instead of "where `image_size` ends" lands in memory the kernel will clear.

## Q2

- Early in boot the kernel zeroes its BSS, the tail of its `image_size` span; the first part of the initramfs sat there, so it was overwritten with zeros (or, with another overlap, the kernel's own data lands on the archive).
- The damage happens at a point that prints nothing; the kernel goes on for about 140 lines and fails only when something later touches the damaged memory, so the last line printed (from networking setup here) only marks how far the boot got; it names neither the cause nor, necessarily, the step that stalled.
- With another overlap the failure moves: a corrupt-archive message, a panic, or a hang. The fingerprint is unreliable; the plan is not.
- The fix is upstream: a boot plan that makes "the initramfs overlaps the kernel's `image_size` span" an error before boot, and a property test that checks no accepted plan overlaps (the reference's suite fails exactly this edit).
- Wrong path: "the kernel reads the initramfs first". It does not; clearing BSS comes before almost everything else.

## Q3

- `vmlinuz-virt` is not an Image: it is a UEFI application (a PE/COFF file, hence `MZ` at offset 0 and `zimg` at 4) carrying a gzip-compressed Image as its payload, so the `ARM\x64` at `0x38` is inside the compressed bytes.
- Starting it means running its decompressor under UEFI firmware, which our direct boot does not have; jumping to it as if it were an Image would run the wrong code.
- Decompressing in the VMM would add a decompressor (a classic source of memory-safety bugs) to the program that holds the hypervisor entitlement, fed with bytes from the internet, at every boot.
- Unwrapping once on the host, with the result checked against a pinned SHA-256 hash, keeps that code out of the VMM, keeps the VMM's input format simple, and makes the boot input reproducible.
- The VMM still recognises the wrapper and refuses it with a named error and a hint, rather than misreading it.

## Q4

- The rule: `p_filesz <= p_memsz` must hold (it does here), and the whole `[p_paddr, p_paddr + p_memsz)` must lie inside guest RAM, computed with `checked_add` so the end cannot wrap.
- The two numbers: the RAM base and the RAM end (base plus size): `p_paddr >= base` and `p_paddr + p_memsz <= end`. With `p_memsz = 2^40` (1 TiB) no guest RAM we allow can hold it, so the file is refused before any byte is written.
- Also checked against the rest of the plan: no overlap with the device-tree slot or another segment.
- Zero only the tail `p_memsz - p_filesz`, through the bounds-checked guest-memory API, in bounded chunks, never by allocating a buffer the size the file asked for.
- Same shape as chapter 04: the guest (here, a file) chose the length, so the length is checked against memory the VMM owns before it is used. Wrong path: "trust `p_memsz`, allocating is the loader's job"; the RAM is the VM's, sized by us, not by the file.
