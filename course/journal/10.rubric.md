# Rubric 10: The Device Tree: the VMM's promise to the guest

## Predict

- Commits to an answer before running, with a reason (for example "the bytes did not change, so the values cannot change", or "the cells are read at different offsets").
- Records what the run showed: `dtb-reader` printed the same `reg=0x40000000+0x4000000`, because it assumes two address and two size cells instead of reading the parent's counts.
- Records that `dtc` reported `reg_format` warnings (16 bytes is the wrong length for one address cell and two size cells), and that the checkpoint's `dtc-clean` step failed.
- Draws the lesson: a reader that shares your assumption cannot catch your bug. Linux reads the cell counts, took a size of `0x4000000000000000` bytes and died in early boot ("Memory doesn't fit in the linear mapping").

## Q1

- 16 bytes: one range of 2 + 2 cells, 4 bytes per cell (`00000000 09000000 00000000 00001000`).
- 8 bytes with `<1>` and `<1>`: one cell for the address, one for the size.
- The length is the first 32-bit word after the `FDT_PROP` token (`0x10`), followed by the name offset; the value follows.
- The counts that matter are the *parent's* (the root's, for the PL011), not the node's own.

## Q2

- The kernel reads the DTB before any device driver runs: memory, `/chosen` and the CPUs first, then devices as drivers bind.
- For a phantom PrimeCell, the AMBA bus code reads the ID registers at `0xFE0` and up before choosing a driver; that is the first access to a device that does not exist.
- With the default policy the access is fatal: `unhandled MMIO read at 0x9050fe0`, exit 3, and the whole VM stops.
- With `--unhandled-mmio log` the reads return zero, the IDs match nothing, the device is never bound ("deferred probe pending") and Linux reaches its shell.
- So our choice of what an unmapped address does is part of the machine: the same wrong DTB is either fatal or harmless depending on it. The DTB and the bus must agree.
- Avoids "the kernel ignores devices it cannot find": it does not know the device is missing until it touches it.

## Q3

- One too high: `dtc` refuses the blob, "String table extends past total size", because offset plus size now passes `totalsize`.
- One too low: the blob is still in bounds, so the check passes, but every property name is read one byte early: most names come out empty and one starts with a stray byte (the end of the `FDT_END` token). `dtc` reports duplicate property names; with `-f` it prints a tree of nameless properties.
- Bounds checks catch some corruption, not all: an offset can be in range and still wrong.
- If the VMM ever read a DTB it would check: the magic; `totalsize` against the buffer and the 2 MiB cap; each block's offset and size against `totalsize`, with overflow-checked additions; alignment (8 for the reservation map, 4 for the structure block); `version` and `last_comp_version`; every `nameoff` inside the strings block; NUL-terminated names; a cap on depth and on the number of tokens.
- Notes these are the same checks as for any guest-controlled length and offset (chapter 04), applied to another format.

## Q4

- Removes disagreement about *where* things are: the address and size in a node's `reg`, the node's unit address and the device's place on the bus all come from the same table row, so moving a device moves all three.
- Does not remove disagreement about *what* a device is or how it behaves: a wrong `compatible` string, a device model whose registers do not match the driver that `compatible` selects (for example ID registers that read zero), wrong cell counts, a missing clock the driver requires, or a node for a device that was never added to the bus.
- Gives one concrete surviving bug, such as the `#address-cells` break of this chapter, which `layout.rs` cannot see.
