# Rubric 14: Booting Linux to a shell

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to a last line and an exit status before running, with a reason.
- Records what the run showed: `timer_probe: no matching timers found`, then `Kernel panic - not syncing: Unable to initialise architected timer.` with a call trace through `time_init`; the last line is the end-of-panic marker; `macvmm` exits 5, from `--timeout`.
- Notices the two halves: Linux named the problem clearly (stage 4 cannot run without a clock), but the VMM never learned that its guest had died, because a panicked kernel spins without exits.
- If they guessed "the output stops with no error": a fair guess (Linux could have hung in delay calibration), corrected by the run; the lesson is to capture, not to assume.

## Q1

- Cheapest first, with what each check needs:
- Did the guest run at all? `--stats` (exit counts, a `PSCI_SYSTEM_OFF` among the `hvc` exits) or a trace filtered to `hvc` answers it without touching the kernel; in the opening run, 82 exits and a clean power-off say "yes, and it finished".
- Is the machine description right? `--dtb-out` and `dtc`: is the DTB where `x0` says, does `stdout-path` or `console=` name the PL011, is `earlycon=` on the command line with the right address?
- Where is the vCPU now, and what did it last touch? The ring dump (`Ctrl-A t` or SIGUSR1): the newest record's PC, time and address tell "stuck in a loop" from "waiting" from "busy with I/O"; a trace filtered to `mmio` shows which device registers it read and what we answered.
- Then devices that must bind for a console: the PL011's identification registers and clock; adding `earlycon` makes the kernel's own messages visible even when the console driver does not bind.
- Wrong path: "rebuild the kernel with more debugging". You have the trace, the DTB and the ring before you touch the kernel.

## Q2

- At least 20 lines, each with a stage and a node or device, for example: `Machine model: macvmm-virt` (root `model`); `psci: PSCIv1.1 detected in firmware.` (`/psci`, our `PSCI_VERSION` answer); `GICv3: CPU0: found redistributor 0 region 0:0x00000000080a0000` (`/intc@8000000`, second `reg` pair); `arch_timer: cp15 timer running at 24.00MHz (virt).` (`/timer`); `ttyAMA0 at MMIO 0x9000000` (`/pl011@9000000` plus its identification registers and `apb_pclk`); `rtc-pl031 9010000.pl031: registered as rtc0` (`/pl031@9010000`); `Freeing initrd memory` (`/chosen` initrd properties).
- Distinguishes "found" from "works": the redistributor line proves the probe succeeded, not that an interrupt was delivered. Delivery is proved by things that need an interrupt: the shell answering typed input (the PL011 receive interrupt, through the GIC), or `timer-latency` finishing 100 sleeps in about 1.07 s (the timer interrupt waking the vCPU), or jiffies advancing in the timestamps.
- The timer line proves Linux found the timer and its frequency; the sleeps prove it fires.
- Wrong path: "the kernel prints what hardware it finds". On Arm it mostly prints what the device tree told it; the hardware it probes (identification registers, GIC revision) is the exception.

## Q3

- Grepping `guests/` for `0xfe0` finds nothing that reads the PL011's identification registers (only the test device's own registers in `hostile-isv0`); Linux read all eight, at `0x9000fe0` to `0x9000ffc`, and the PL031's too.
- Other parts only Linux used: the `apb_pclk` fixed clock, the `/chosen` command line with `console=` and `earlycon=`, the initrd properties, PSCI and SMCCC discovery calls (`PSCI_FEATURES`, `SMCCC_ARCH_FEATURES`, `TRNG_VERSION`, `VENDOR_HYP_CALL_UID`), the OS-lock debug registers, the GIC redistributor's identification register `GICR_PIDR2`, the timer's interrupt properties.
- Each is something the device tree or the machine promised, and a test guest written to exercise one device never asked for.
- On the chapter 09 guess: with zeros in the identification registers, the AMBA bus matches no driver, no `ttyAMA0` appears, user-space output is lost, and the boot still exits 0. Says whether their guess matched, and what they had missed if not (commonly: "the UART still works because the guest only writes `DR`", true for our test guests, false for Linux).

## Q4

- Names three real gaps, for example: persistent storage (the root file system lives in an initramfs in RAM and vanishes at power-off); networking; more than one CPU; fast bulk I/O (178,000 exits for 64 KiB of console text); booting through firmware so other operating systems and stock images work; a clean reboot path.
- Defends an order with a reason, not only a ranking: for example, fast I/O first because a disk or network built on per-register exits would be unusably slow, and virtio is the mechanism both need; then storage, because a VM that forgets everything is a demo; then several CPUs, which multiply every concurrency bug and are easier to debug once devices are stable.
- Accepts that the order depends on what the VM is for (a build server, a desktop, a test rig) and says which use they assumed.
- Wrong path: "nothing, it boots". Nudge: where did the file system live, and where did it go when you typed `poweroff -f`?
