## Q1

- The function ID is in `w0` (the low 32 bits of `x0`): `0x8400000A`, `PSCI_FEATURES`.
- The function being asked about, `0x84000099`, is the first argument, in `x1` (read as `w1`, since this is a 32-bit-convention call).
- The result comes back in `x0`: -1, `NOT_SUPPORTED`, which the guest prints as `features(0x84000099)=-1`.
- The VMM writes the result into the vCPU's `x0` before resuming; the guest reads it after its `hvc` as an ordinary return value. "The registers are the API": no shared memory, no special mode.
- Does not answer `x30` or the stack: SMCCC results follow the same registers as an ordinary function call's.

## Q2

- Returning 0 hides the gap: the guest proceeds on a lie (a feature wrongly detected as present or absent, a status read as "all clear"), and nothing anywhere reports it.
- Injecting UNDEF is what real hardware does for a register it does not have; a guest that probes optional registers can catch it and fall back, but a guest that assumes the register exists will crash, loudly and where the problem is.
- `PMUVer = 0` tells the guest there is no performance monitoring unit, so its registers are UNDEFINED by the architecture; injecting UNDEF keeps our answer consistent with the ID register.
- `LO = 1` says limited ordering regions exist, so `LORID_EL1` must not UNDEF; reading it as zero is a real answer ("zero regions").
- The right policy is per register, agreeing with the ID registers, with a written reason next to each row; the default for anything unknown is UNDEF, never "let it through".

## Q3

- Under HVF both instructions trap to the VMM (exception classes `0x16` and `0x17`), so the VMM can serve both; "`smc` is for real firmware, so it will not trap" is wrong.
- An `hvc` executed and is a call, so the saved PC already points after it; an `smc` was intercepted before it executed, so the saved PC points at it (the captures show the same call at `0x4008137c` after `hvc` and `0x40081378` at `smc`). Without the advance, the guest would repeat the `smc` forever.
- `method = "hvc"` tells the guest which conduit to use for every PSCI call; it is a promise from the VMM. Accepting `smc` as well is a policy decision, not something the guest may rely on.

## Q4

- Without a standard, every VMM (and every board) would need its own power-off and CPU-start driver in the kernel, and the kernel would need to know which one it was running on.
- With PSCI, one kernel boots on any machine whose device tree has a `psci` node: the node names the conduit, and the function IDs are fixed by Arm.
- A standard is also a contract the VMM can be tested against: our dispatcher's table is the PSCI specification's table.
- Names the cost of not standardising in concrete terms (count the VMMs, firmwares and boards).
