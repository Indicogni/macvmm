## Predict

- Puts a ledger row next to each guess (for example: kernel-only instructions, row 1; the disk or console, row 3; the clock, row 7), and notes which rows nobody guessed.
- Commits to one answer for mode D before running it, with a reason.
- Afterwards records what mode D showed: (c), only the instructions that trap (the privileged ones, `GETMODE` made to trap, the console stores and the app's system calls, which the VMM passes on to the guest kernel: 13 from the listing); and names "the VMM runs every instruction" as the emulator's behaviour (mode C), not a VMM's.
- For mode E, records that the guest did notice: `GETMODE` answered "user" and the toy kernel panicked, with no trap.

## Q1

- Compares the three: an intervention for every instruction under interpretation, only the trapping ones under trap-and-emulate, only what the VMM chose to trap under hardware assist (from the listing: 1,000, 13 and 4 with the interrupt switch and console chosen; or the lab's counts).
- Names the deciding number as the VMM interventions (traps) per guest instruction, not the number of guest instructions.
- Explains why: each intervention costs far more than a native instruction (about a thousand times in the lab's stated toy model), so the fraction of instructions that need the VMM sets the slowdown.
- Notes that the toy cost model is invented, and that the real cost of one stop is measured later, on the Mac.

## Q2

- Names `GETMODE`: sensitive (it reads the mode the VMM must control) but not privileged (it does not trap in user mode).
- Explains that the VMM never ran at that moment: no trap means no turn, so it could not substitute the virtual mode "kernel".
- Explains why afterwards is too late: the wrong answer is already in a register and the guest has branched on it; the VMM cannot tell, from outside, which later behaviour came from that answer.
- Connects it to Popek and Goldberg's condition: every sensitive instruction must be privileged for trap-and-emulate to work.

## Q3

- Separates what the toy showed from what a real machine adds (the first registers, the description of the machine).
- Set up the guest's memory (in the toy, the second base register: the second translation stage).
- Set the first registers, so the guest starts at the right place.
- Describe the machine to the guest.
- Answer device accesses (the console range it chose to trap).
- Answer requests and decide what each stop means.
- Does not list "running the guest's instructions": under hardware assist the processor does that. (A common wrong answer is "it translates the guest's instructions"; that is emulation.)

## Q4

- A table close to: emulation, such as QEMU, which translates blocks rather than interpreting one instruction at a time (any guest, slow); trap-and-emulate on IBM mainframes, CP-67 and VM/370 (fast, but needs every sensitive instruction privileged); VMware's binary translation (unmodified guests on x86; a large, hard translator, translation time and a code cache); Xen's paravirtualization (no translator; a modified guest); Intel VT-x or Arm EL2 (unmodified guests natively; at first every stop was an expensive round trip and memory was still shadowed, until the second translation stage).
- Paravirtualization's cost: the guest must be modified, so a guest whose source you cannot change (or cannot rebuild) cannot run; the VMM and guest must also agree on the hypercall interface.
- Survival: hypercalls a guest makes on purpose to ask for a service, such as powering off (chapter 08), and devices designed for virtual machines, which talk to the VMM through shared memory (chapter 15).

## Q5

- Interpretation still works unchanged: the emulator answers the instruction in software.
- Binary translation still works: the translator rewrites the new instruction like `GETMODE`.
- Paravirtualization still works for guests that are edited not to use it.
- Plain trap-and-emulate breaks: the instruction is sensitive and unprivileged, the exact failure of mode E.
- Hardware assist is fine only if the guest runs in a real kernel mode where the answer is true, or if the more privileged level can be told to trap it.
- The request to the designers: make it trap when run deprivileged, or let the level above choose to trap it (a configurable trap), so every sensitive instruction gives the VMM a turn.
