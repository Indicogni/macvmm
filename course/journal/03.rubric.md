# Rubric 03: A guest of your own, and what an exit costs

Ideas a strong answer contains. Compare, do not copy: an answer in your own words that reaches
the same mechanism is a full answer.

## Predict

- Commits to a number before running, with a reason (for example "it switches exception levels and wakes a thread, so it cannot be a nanosecond").
- Records what `exit-bench` printed: about 1.4 µs per round trip on an idle Mac (roughly 1.3 to 2 µs, more on a loaded host), so microseconds, not nanoseconds.
- Divides: about 1,430 ns / 0.233 ns, so one exit costs as much as several thousand (roughly six thousand) stores.
- Notes that the store figure includes the loop's own instructions, so a store alone is, if anything, cheaper still.

## Q1

- Estimates before measuring: 4,096 bytes is 4,096 exits (one per byte), so at least 4,096 x about 1.4 µs, roughly 6 ms, before any formatting work; at the traced `hello` rate of about 4.4 µs per exit, about 18 ms.
- Measures with the trace's `t_ns`: the gap between consecutive DEBUG_PUTC records (several µs in the `hello` trace, more than `exit-bench`'s figure because printing and tracing add work), times the byte count, or the first and last timestamps.
- Concludes that the cost is per exit, not per byte: a device that takes data one register write at a time pays a full world switch for every byte.
- Infers the design consequence: real devices should accept data in bulk, through memory both sides can read, with one notification (one exit) for many bytes; this is what virtio does from chapter 15 on.
- Does not answer "nanoseconds, it is a function call"; the trace shows the gaps.

## Q2

- `sp` is 0: a fresh vCPU's registers are zero, the monitor sets only the PC, PSTATE and `x0`, and the `sp` probe printed `A` (its test for exactly 0).
- The first stack use, `sub sp, sp, #0x20` in `guest_main`, wraps to `0xffff_ffff_ffff_ffe0`, and the store through it uses an address no memory could have.
- With translation off, that is an address size fault taken at the guest's own level, EL1, through its own vector table (`VBAR_EL1 + 0x200`, `0x40080a00`), so it is not a guest-physical access and EL2 has nothing to forward: no VM exit.
- The handler's first instruction moves `sp` down again and stores through it, so it faults again, forever: a silent hang, found only by `--timeout`, whose `canceled` record shows the PC at `0x40080a00`.
- Generalises: nothing in the CPU provides a stack; a boot protocol may not promise one either, so `_start` must set it before any compiled code runs, and even a fault handler needs it.

## Q3

- Today the monitor writes every byte to its output, one exit and one write per byte, as fast as the guest asks: the guest controls how much host output and host CPU time it consumes.
- Names the harm concretely: a terminal or log flooded, a pipe that fills up and blocks the vCPU thread, a disk filled by a redirected output, a host CPU kept busy.
- Proposes a limit and what happens at it: a byte or rate cap per second, a total cap with a "truncated" marker, or dropping output when the consumer is slow, rather than blocking.
- Connects it to what the reference already does: the `unknown SMCCC function` warnings in `exit-bench` are rate-limited (ten, then one per thousand), and the trace file has a size cap, because the guest decides how often it calls.
- States the principle: a hypercall is a request from an untrusted program, not a trusted debug channel; who calls it decides how often.
