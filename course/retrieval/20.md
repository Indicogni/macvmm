# Retrieval 20: SMP: many vCPUs, many threads

## R1
Q: A guest runs with `--cpus 20`. What is `MPIDR_EL1` of vCPU 17, and what does its `cpu@…` node in the device tree carry as `reg`?
A: Aff1 = 17 / 16 = 1 and Aff0 = 17 % 16 = 1, plus bit 31, which always reads 1: `0x8000_0101`. The device tree's `reg` is the affinity part only, without bit 31: `0x101`, so the node is `cpu@101`. A PSCI `CPU_ON` for that CPU names it as `0x101` too.

## R2
Q: vCPU 0 calls `CPU_ON` for CPU 1 twice in a row with a valid entry point. The first call returns 0. Which values can the second return, and why is either one correct?
A: -5 (`ON_PENDING`) or -4 (`ALREADY_ON`). The first call moved CPU 1 from off to "on pending" and filled its mailbox. If CPU 1's thread has not yet taken the mailbox, the second call sees "on pending"; if it has, it sees "on". Which one wins is host thread timing; both say "no second start".

## R3
Q: Why does the VMM create every vCPU at startup, one after the other, instead of creating a vCPU when the guest asks for it with `CPU_ON`?
A: Hypervisor.framework gives each vCPU the next redistributor frame in creation order, and the guest finds its frame by its MPIDR, so creation order must equal index order. The interrupt controller's set of CPUs is fixed once a vCPU has run, so a late vCPU is not possible. And a `CPU_ON` can then only fill the mailbox of a thread that already exists: a guest cannot make the VMM spawn threads.

## R4
Q: A vCPU thread is blocked on a mutex inside an MMIO handler when `--timeout` expires. The control thread sets the stop flag and calls `hv_vcpus_exit` on every vCPU. What happens to that thread, and why?
A: Nothing: a kick only forces a vCPU out of `hv_vcpu_run`, and this thread is not in it. It stays blocked until the mutex is released. That is why no lock may be held while waiting on anything unbounded, and why a lock-order deadlock survives the VMM's own timeout.

## R5
Q: `CPU_ON` arrives for target `0x8000_0001` (bit 31 set). The machine has a vCPU whose MPIDR is `0x8000_0001`. What does our VMM answer?
A: `INVALID_PARAMETERS` (-2). A PSCI target carries only the affinity fields (Aff3 in bits 39 to 32, Aff2 to Aff0 in bits 23 to 0). Bit 31 is not an affinity bit, so the target names no CPU; the device tree's `reg` never has it.

## R6
Q: Thread A takes the device lock, then the counter lock. Thread B takes the counter lock, then the device lock. Each lock is held only for a few microseconds. Is this program safe if it passes a one-minute test?
A: No. Both threads can each take their first lock and then wait forever for the other's: a deadlock. Short holds only make the bad interleaving rare, not impossible; under load it happens. The cure is one global order (device, then counter) or no second lock at all (an atomic counter).

## R7
Q: A secondary vCPU starts after `CPU_ON(target, 0x4008_0078, 0x33)`. Which registers does the VMM set before its first run, and to what?
A: PC = `0x4008_0078`, `x0` = `0x33` (the context ID), `x1` to `x3` = 0, PSTATE = `0x3c5` (EL1h, all four masks set), and `SCTLR_EL1` with the MMU and caches off. The entry point is checked first: 4-byte aligned and inside RAM, or the call returns `INVALID_ADDRESS` (-9).

## R8
Q: Two vCPUs write the PL011's data register at the same moment. Without the device's `Mutex`, what stops the race in our Rust VMM?
A: The compiler. The bus is shared by reference between vCPU threads, so everything inside it must be `Sync`, and a device is not; and an `Arc` gives only shared access, so `write(&mut self, …)` cannot be called through it. Removing the lock is a compile error, not a run-time race.
