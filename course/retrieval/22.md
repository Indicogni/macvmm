# Retrieval 22: FreeBSD through U-Boot EFI (SHOULD)

## R1
Q: FreeBSD's kernel prints `vtblk0: host requires unsupported maximum segment size feature` and stops at `mountroot>`, although U-Boot and FreeBSD's loader read the same virtio disk a few seconds earlier. Where is the problem, and what do you change in the VMM?
A: The device worked; FreeBSD's driver refused one promise in it. The device offered `VIRTIO_BLK_F_SIZE_MAX` with `size_max` = 64 KiB, and FreeBSD's `vtblk` driver will not attach to a device whose segment limit is below its largest transfer (1 MiB on arm64), so no disk, so no root file system. U-Boot and Linux honour the small limit, which is why they worked. Stop offering the feature: our device copies data in 64 KiB pieces whatever the segment size, so it never needed the promise.

## R2
Q: You delete `apb_pclk` from the PL011 node's `clock-names` and boot both guests. Which one notices, and what does each print?
A: Only Linux, and quietly. Its AMBA bus asks for a clock named `apb_pclk` before it binds any PrimeCell, finds none, and never binds the UART: no `ttyAMA0` line, the early console keeps printing, then `Warning: unable to open an initial console.`, and the init program's own output is lost. FreeBSD binds its PL011 driver by `compatible` alone and boots to `login:` unchanged.

## R3
Q: No EFI boot variables survive between our runs. How does U-Boot still find FreeBSD's loader on the disk?
A: With no `Boot####` entry to follow, UEFI falls back to the removable-media path: on the first disk's EFI system partition it runs `\EFI\BOOT\BOOTAA64.EFI`, the fixed name for 64-bit Arm. FreeBSD's image puts `loader.efi` there. Variables cannot persist because our flash ignores writes.

## R4
Q: The exit trace of a FreeBSD power-off shows `PSCI_SYSTEM_OFF` from `pc=0xbf69a1b8`, an address near the top of RAM rather than in the kernel. Who made the call, and why there?
A: U-Boot did, in its EFI runtime services. FreeBSD's `shutdown -p now` asked the firmware to power off through the runtime service `ResetSystem`, and U-Boot, which had relocated itself to the top of RAM and left that code in place after `ExitBootServices`, implements it with PSCI `SYSTEM_OFF` over `hvc`.

## R5
Q: Why does every FreeBSD run boot from `cp -c` of the cached image instead of the cached file itself?
A: The guest writes to its disk (logs, entropy, the partition resize check), so booting the cached file would change it and break its sha256 pin. An APFS clone is created instantly, shares every block, and copies only the blocks the guest writes, so each run starts from the same pinned bytes.

## R6
Q: QEMU's device tree gives each virtio-mmio node `interrupts = <0 16 1>`; ours says `<0 16 4>`. Should we copy QEMU's value?
A: No. The last cell is the trigger type: 1 is edge, 4 is level-high. Our virtio-mmio device drives a level line that stays high until the driver acknowledges, so 4 is the truth about our machine. A DTB describes the machine we built; QEMU is a reference for *which* properties guests expect, not a source of values to copy blindly.

## R7
Q: FreeBSD printed its banner. Name three observations from a full run that each prove more of the machine works than the banner does.
A: Any three of: root mounted from `vtbd0p3` (virtio-blk reads through the GIC's interrupts); `Multiprocessor System Detected: 2 CPUs` with a `PSCI_CPU_ON` exit in the trace (SMP); `login:` answered and `uname -sr` echoed back (UART input and interrupts both ways); the right wall-clock date (the PL031); a clean `shutdown -p now` ending in exit code 0 (PSCI through EFI runtime services).

## R8
Q: Linux boots on your VMM and FreeBSD does not. A colleague says "FreeBSD is just pickier, ignore it." What do you check before agreeing?
A: Where FreeBSD read the thing it rejected (a DTB property, a feature bit, a register) and what the primary sources say: the specification (virtio, the device-tree binding), the driver's own source, and what QEMU `virt`, the machine both guests are tested on, presents. If QEMU does it differently and both guests work there, our machine is the odd one out. One guest booting proves only that guest's needs are met.
