# Retrieval 13: Loading kernels: arm64 Image, initramfs and ELF

## R1
Q: The eight bytes at offset `0x10` of an Image header are `00 00 2a 02 00 00 00 00`, and `text_offset` is 0. Where does the kernel's memory start and end in our plan?
A: The field is `image_size`, little-endian: `0x022a0000`. The kernel starts at the 2 MiB-aligned base `0x4020_0000` plus `text_offset` 0, so it owns `0x4020_0000..0x424a_0000` (start plus `image_size`, end exclusive).

## R2
Q: That kernel ends at `0x424a_0000`. Where does our plan put a 9 MB initramfs, and which part of that choice comes from the boot protocol and which from us?
A: At `0x4260_0000`, the end rounded up to the next 2 MiB boundary. The protocol only requires that it lie outside the kernel's `image_size` span and, with the kernel, inside one 1 GiB-aligned window of at most 32 GiB; the 2 MiB rounding is our choice, to keep the numbers readable.

## R3
Q: A `--kernel` file begins with the bytes `4d 5a` and has `zimg` at offset 4. What is it, what does our VMM do with it, and what do you run instead?
A: An EFI zboot wrapper: a compressed kernel packaged as a UEFI program (the `MZ` is the PE/COFF signature). The VMM refuses it with "EFI zboot image" and exit code 2 before creating a VM; `cargo xtask unzboot` (run by `scripts/fetch.sh linux`) unwraps it on the host into the raw Image.

## R4
Q: An Image's `flags` field is `6`. Does our loader accept it?
A: No. Bit 0 is 0 (little-endian, fine), but bits 1 and 2 read `0b11` = 3, "64 KiB pages", which Apple Silicon does not implement. The loader refuses it with a named error rather than let the kernel die in early boot with no output.

## R5
Q: A header claims `image_size = 0xFFFF_FFFF_FFFF_FFFF`. Why does `load + image_size <= ram_end` not catch it, and what does?
A: With wrapping arithmetic the sum overflows to a small number (here `0x401F_FFFF`), which passes the comparison; in a Rust debug build `+` panics instead. `load.checked_add(image_size)` returns `None` on overflow, and the range check (`RamRange::contains`) treats that as "outside RAM", so the plan fails with exit code 2.

## R6
Q: An ELF program header of type `PT_LOAD` says `p_filesz = 0x100` and `p_memsz = 0x80`. What does the loader do?
A: Refuse the file. A segment cannot hold more file bytes than memory: `p_filesz <= p_memsz` must hold, and the difference is the zero-filled tail (the BSS). Copying `p_filesz` bytes into a `p_memsz` slot would write past the segment.

## R7
Q: List the register values our vCPU starts a Linux kernel with, and the one system-register setting that goes with them.
A: PC = the kernel's first byte (`0x4020_0000`), `x0` = the device tree's address (`0x4000_0000`), `x1`, `x2` and `x3` = 0, `CPSR` = `0x3c5` (EL1h with D, A, I and F masked). The MMU is off: `SCTLR_EL1.M` (and the cache-enable bits C and I) cleared.

## R8
Q: `macvmm run --dry-run ...` printed a full boot plan and exited 0 from a binary that lacks the hypervisor entitlement. What does that prove, and why is it worth designing for?
A: That planning makes no Hypervisor.framework call: without the entitlement, `hv_vm_create` would have failed with `HV_DENIED`. Keeping placement a pure computation means every overlap and bound can be printed, unit-tested and property-tested on any machine, and is checked before a VM exists.
