# Retrieval 17: virtio-rng (worked) and virtio-console (faded)

## R1
Q: A guest posts one chain to virtio-rng: a 64-byte readable descriptor, then a 32-byte writable one. How many bytes does the device write, where, and what `len` goes in the used ring?
A: 32 bytes, all into the writable descriptor; the readable one is never written, not even with its own bytes. The used `len` is 32: the number of bytes the device actually wrote, never the chain's total of 96.

## R2
Q: Ten `QueueNotify` writes arrive while the worker thread is busy with a batch. How many times will it call `process_queue` for that queue afterwards, and why is that safe?
A: Between one and ten times; usually once. Each notify only sets the queue's bit in the pending mask, and ten sets of one bit are one bit (notify coalescing). It is safe because a notify carries no data: it says "look at the ring", and one look sees every buffer published before it.

## R3
Q: Your worker's `notify` sets the pending bit under the mutex but forgets `notify_one()`. Linux boots, prints `hw_random=virtio_rng.0`, then nothing until `--timeout`. Who is waiting for whom?
A: The guest's driver waits (in WFI, idle) for the used-buffer interrupt; the worker sleeps on the condition variable waiting for a bell that never rings. The pending bit is set but nobody looks at it: a lost wake-up. Host CPU stays near 0%, because everyone is asleep.

## R4
Q: Linux reads 1 MiB from `/dev/hwrng` and the trace shows 16,387 `QueueNotify` writes. Estimate the size of each buffer the driver posts and the number of exits per request.
A: 1,048,576 / 16,384 = 64 bytes per buffer (the other two or three are the kernel's own reads, which ring even when `dd` reads nothing). Each request costs about three exits: the doorbell write, then the `InterruptStatus` read and the `InterruptACK` write in the driver's interrupt handler. Exits follow buffers posted, not bytes.

## R5
Q: Writing 4,096 bytes to the PL011 cost 8,194 extra exits; writing them to `/dev/hvc0` in one `write` cost 4. At about 1.43 microseconds per exit, how long does each spend in exits alone?
A: PL011: 8,194 x 1.43 us, about 11.7 ms (two exits per byte: a flag-register read and a data-register write). virtio-console: 4 x 1.43 us, about 6 us. The ratio, about 2,000, comes from the number of exits, not from faster device code.

## R6
Q: Why does a virtio-console need two queues when the PL011 needed none?
A: The device cannot allocate guest memory; it can only write into buffers the driver posted. Host input arrives unprompted, so receive needs a standing pool of empty writable buffers posted in advance, while transmit buffers are readable and posted only when the guest has text: two queues. A UART instead moves one byte at a time through a register in either direction.

## R7
Q: The console's receive queue has posted buffers but the host has typed nothing. What must one pass of `process_rx` do, and why?
A: Pop nothing and return. Popping a chain with no input to put in it would force the device to return it empty (`len` 0), which the driver would take as a zero-byte read. Host bytes wait in the bounded input queue; when they arrive, the input hook rings the worker's doorbell for queue 0, exactly as a guest notify would.

## R8
Q: The transmit path of the console writes guest bytes into the sink. Name two things that must happen between the guest's buffer and your terminal.
A: The bytes are copied once into a fresh, zeroed buffer (so a guest rewriting its buffer cannot change them after the check), and they pass through the sink's output filter, which strips dangerous escape sequences on every sink, a file included. The worker also never calls `write(2)` itself; the sink's writer thread does, so a stalled terminal cannot hold the device lock.
