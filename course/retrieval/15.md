# Retrieval 15: Rings and a doorbell: the virtio-mmio transport

## R1
Q: On our board, a driver reads the 32-bit word at `0x0a00_0608` and gets 0. Which register of which slot is that, what must the driver conclude, and should the device tree have a node at `0x0a000600`?
A: Slots start at `0x0a00_0000` and are `0x200` apart, so `0x0a00_0600` is slot 3 and offset `0x008` is `DeviceID`. 0 means "no device here": the specification says the driver MUST ignore it. There is no node, because only populated slots are listed; the empty slot still answers on the bus so that a guest which scans the fixed addresses gets a defined answer rather than an unhandled-MMIO fault.

## R2
Q: A driver writes `Status` = 0, 1, 3, then `0xb`, and reads back `0x3`. What happened, and what should the driver do next?
A: `FEATURES_OK` did not latch: the device refused the accepted feature set, because it contained a bit the device never offered or lacked `VIRTIO_F_VERSION_1`. The driver must treat the device as unusable (it may set FAILED) rather than carry on.

## R3
Q: A driver writes `DriverFeaturesSel` = 0, `DriverFeatures` = 0, `DriverFeaturesSel` = 1, `DriverFeatures` = 1. Which feature bits did it accept?
A: Only bit 32: the selector picks which 32-bit half of the 64 feature bits a write covers, so value 1 in the high half (selector 1) is bit 32, `VIRTIO_F_VERSION_1`, and the low half is empty.

## R4
Q: A guest reads 2 bytes at offset `0x000` of a populated slot, then 2 bytes at offset `0x100` of the same slot, whose device has an 8-byte config space. What does each read return?
A: The first is a control register, which accepts only aligned 32-bit accesses: it reads as zero, with a rate-limited warning (RAZ/WI). The second is config space, which accepts 1, 2, 4 or 8 bytes inside the device's config length, so it returns the device's first two config bytes.

## R5
Q: Queue 0 is not ready. The driver writes `QueueDescLow` = `0x10`, then `QueueDescHigh` = `0xffff_ffff`. What is the descriptor table's address, and is anything checked yet?
A: `0xffff_ffff_0000_0010`, assembled as `high << 32 | low`. Nothing about it is checked when the halves are written; the transport only records it. It is checked once, at `DRIVER_OK`, and this one lies far outside RAM, so the device would set `DEVICE_NEEDS_RESET`.

## R6
Q: Linux's 12,093-byte boot log cost 32,795 MMIO exits at the PL011, and one exit costs at least 1.4 µs. Estimate the exits and the time for one 4 KiB block sent the same way.
A: 32,795 / 12,093 is about 2.7 exits per byte (one write of the data register, plus reads of the flag register). 4096 × 2.7 is about 11,000 exits, and 11,000 × 1.4 µs is at least 15 ms for one block, before any real work (an MMIO exit costs more than the bare round trip chapter 03 measured).

## R7
Q: After `DRIVER_OK`, the driver selects a queue that was never made ready and writes `QueueNum` = 8 and `QueueReady` = 1. What does our transport do, and why?
A: It ignores both writes with a warning: `DRIVER_OK` freezes every queue register. The rings were validated at `DRIVER_OK`; a queue configured afterwards would have addresses nobody checked.

## R8
Q: The driver sets `DRIVER_OK` while queue 0's used ring straddles the end of RAM. What does it read from `Status` and `InterruptStatus`, and what is the interrupt line doing?
A: `Status` reads `0x4f` (`0xf` plus `DEVICE_NEEDS_RESET`, 64), `InterruptStatus` reads 2 (configuration change), and the line is high. The device was never activated; it does nothing more until the driver writes 0 to `Status`.

## R9
Q: `InterruptStatus` is 3, and the driver writes 1 to `InterruptACK`. Is the line high or low afterwards?
A: Still high: bit 0 is cleared, bit 1 remains, and the line is level-triggered, high exactly while `InterruptStatus` is not zero. It drops only when the driver also acknowledges bit 1.
