# Retrieval 25: Hardening: threat model, fuzzing and sandboxing

## R1
Q: Guest RAM has two regions, `0x4000_0000` (256 KiB) and `0x4008_0000` (64 KiB). A device validates a buffer `0x4002_e6e9 + 0x5_193a` by checking that its first byte and its last byte are each in RAM. Does it pass, and should it?
A: It passes and should not. The first byte, `0x4002_e6e9`, is in the first region; the last, `0x4008_0022`, is in the second. The 256 KiB between them (`0x4004_0000..0x4008_0000`) is not RAM, and the two regions are separate host allocations, so one copy would run off the first. The check must be "the whole span `[addr, addr + len)` lies inside one region", with `checked_add` (or wider arithmetic) for the end.

## R2
Q: Your fuzzer reports a failure at iteration 23,338,941 of `--seed 1`. A colleague on another Mac wants to see the exact input. What do they run, and why does it not take 23 million iterations?
A: The same target with `--seed 1`, or, faster, `--replay` on the saved file. Iteration `i` draws its generator from `derive(seed, i)`, so any single iteration can be regenerated directly from the two numbers; the earlier iterations do not have to be replayed. That only holds for single-threaded targets: a target with a racing thread, like `virtqueue_race_only`, can fail at a different iteration on every run.

## R3
Q: The hop budget was removed from the chain walker, yet the fuzzer reported no hang: the walk ended by itself. What ended it, and what in the fuzzer still caught the bug?
A: The chain looped, adding its buffer lengths to the per-chain total, until the total passed the byte cap (`max_total`) and the walker returned `TooLarge`. The bug was caught by an invariant, not by a hang or a panic: at most `2N + 1` descriptor reads per pop, and the log showed 2,838 for a two-entry queue. A fuzzer that only watched for crashes would have missed it.

## R4
Q: Name a bug class that `#![forbid(unsafe_code)]` does not prevent in a VMM, and give one concrete instance a guest could trigger.
A: Any of: a logic bug (a range check with wrapping arithmetic accepts a buffer outside RAM); resource exhaustion (a guest-grown trace file with no cap); an infinite loop (a descriptor whose `next` is itself, with no hop budget); TOCTOU (a descriptor `len` read once to check and again to use, while another vCPU rewrites it); a confused deputy (an output path that names the guest's own disk image). All are memory safe and all are wrong.

## R5
Q: macvmm applies its sandbox profile after opening the disk image read-write. The guest then writes a sector. Does the `pwrite` succeed, and would `open("/etc/hosts")` at the same moment?
A: The `pwrite` succeeds: the sandbox checks a resource when it is acquired, and the descriptor was acquired before the lockdown. The `open` is refused with "Operation not permitted"; the unified log shows it as `file-read-metadata /etc`, because resolving the symbolic link `/etc` is already a denied lookup. That is why the lockdown runs after every file is open and before the first guest instruction.

## R6
Q: The hostile guest calls `SYSTEM_RESET` on every boot. Which exit code must macvmm end with, why that one and not 0, and why is exit code 1 never acceptable here?
A: Exit code 3, a fatal guest stop, after the eleventh reset within 10 seconds (the reset storm limit). Rebooting forever would make the host do unbounded work for a guest that never makes progress, so the defined response is to stop. Exit code 1 means the VMM itself failed (an error or a panic); a guest that can cause it has found a bug.

## R7
Q: A planted bug fires only when the first and third buffers of one chain share an address. A blind fuzzer picks every address uniformly from all 2^64 values. Roughly how often will two buffers match, and what made our fuzzer find it in about two minutes?
A: About one pair in 2^64: in practice never. Our structure-aware mutation aims addresses at a short list of special places (region edges, the hole, the rings themselves), so two descriptors receiving the same special, here the used ring at `0x40003000`, happens every few million iterations. The bug was findable because the mutator's grammar contained the shape; a shape outside that grammar stays invisible.

## R8
Q: Why does macvmm set `RLIMIT_CORE` to 0 for both the soft and the hard limit, rather than only the soft one?
A: A core dump of macvmm would be a file holding guest RAM. With only the soft limit at 0, any process may raise it again up to the hard limit (`ulimit -c unlimited` in a wrapper script), and the core dumps return. With the hard limit also at 0, raising it needs root, so "no core dumps" becomes irreversible for the process.
