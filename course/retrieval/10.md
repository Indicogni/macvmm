# Retrieval 10: The Device Tree: the VMM's promise to the guest

## R1
Q: A node's parent says `#address-cells = <2>` and `#size-cells = <1>`. The node's `reg` describes two ranges. How many bytes long is the `reg` property?
A: Each range is 2 + 1 = 3 cells, and a cell is 4 bytes, so one range is 12 bytes and two ranges are 24. The counts come from the parent, not from the node itself.

## R2
Q: The first eight bytes of a blob are `d0 0d fe ed 00 00 04 f7`. What is it, and how big is it?
A: A flattened device tree: `0xd00dfeed` is its magic number. The next big-endian 32-bit word is `totalsize`, `0x4f7` = 1271 bytes. Read little-endian, the same bytes would give `0xf7040000`, which is why the byte order matters.

## R3
Q: Why can an arm64 kernel not find the PL011 by reading every address in the first 4 GiB and looking for a UART?
A: Nothing on that bus answers "who is here?", and an address with no device behind it does not return a polite "nothing" either: on real hardware it can fault or hang, and in our VMM it is an unhandled access that stops the guest (exit code 3 by default). Even the PrimeCell ID registers help only once you know where the device is. So somebody has to tell the kernel: the DTB.

## R4
Q: Two nodes each have a `compatible` property. How many times does the word `compatible` appear in the blob, and where?
A: Once, in the strings block: property names are stored there once and referred to by offset (`nameoff`). The values (`"arm,pl011"`, `"arm,pl031"`) are not names; they sit in the structure block after each `FDT_PROP` token.

## R5
Q: Your writer opens `/cpus`, opens `cpu@0`, closes it, and then adds `#size-cells` to `/cpus`. What should happen, and why?
A: An error. The format requires every property of a node to come before its first child node, because a reader walks the token stream once and attaches each property to the node it is in. The reference writer refuses it as `PropAfterChild` instead of writing a tree a kernel would misread.

## R6
Q: A guest's first instruction runs with `x0 = 0x40000000`. What does an arm64 kernel expect to find there, and what two rules does the address obey?
A: The device tree blob: Linux's boot protocol says `x0` holds its physical address. It must be 8-byte aligned and the blob at most 2 MiB long, in RAM. Our VMM puts it at the start of RAM.

## R7
Q: You add a node `pl031@9050000` to the DTB but no device to the bus. Linux boots. With the default unhandled-access policy, what does `macvmm` print, and why at that address?
A: `unhandled MMIO read at 0x9050fe0`, then exit code 3. The AMBA bus code reads a PrimeCell's ID registers, at offsets `0xFE0` to `0xFFC`, before it picks a driver, so the first access to the phantom device is the ID read. With `--unhandled-mmio log` the reads return zero and the device is left unbound ("deferred probe pending").

## R8
Q: A node says `compatible = "arm,pl011", "arm,primecell"`. Why two strings, and in which order are they tried?
A: Most specific first. A kernel looks for a driver that knows `arm,pl011`; the second string says what family the device belongs to (an Arm PrimeCell, with ID registers), which a more general driver or bus can use.

## R9
Q: `/cpus` says `#address-cells = <1>` and `#size-cells = <0>`. How long is `cpu@0`'s `reg`, and what does it hold?
A: 4 bytes: one address cell and no size. It holds the CPU's identity (its MPIDR affinity, here 0), which is why the node is called `cpu@0`.
