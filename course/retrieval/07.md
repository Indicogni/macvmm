# Retrieval 07: The exit loop: decoding syndromes and emulating MMIO

## R1
Q: A data-abort exit carries the syndrome `0x93820046`. Without looking at guest memory, say the direction, the size and the register of the access, and name one instruction that fits.
A: EC is `0x93820046 >> 26 = 0x24`, a data abort from the guest. Bit 24 (ISV) is 1, so the note is valid. SAS (bits 23:22) is 2, so 4 bytes; SSE is 0; SRT (bits 20:16) is 2; SF is 0, so a 32-bit `w` register; WnR (bit 6) is 1, a write. A 4-byte store from `w2`, such as `str w2, [x1]`.

## R2
Q: A trapped store has SRT = 31. What value does the VMM send to the device, and why must it never pass 31 to `hv_vcpu_get_reg`?
A: Zero: in the data-register field of a load or store, 31 means `xzr`, which reads as 0. In Hypervisor.framework's register numbering, 31 is `HV_REG_PC`, so passing it through would send the guest's PC to the device (and a load into `xzr` would overwrite the PC).

## R3
Q: The test device holds `0x8001` at some offset. What ends up in the destination register for `ldrh w3`, `ldrsh w3` and `ldrsh x3` from that offset?
A: `ldrh w3` gives `0x8001` (zero-extended). `ldrsh w3` gives `0xffff8001`: sign-extended to 32 bits, and writing a `w` register clears the upper half. `ldrsh x3` gives `0xffffffffffff8001`, sign-extended to 64 bits. SSE says whether to sign-extend; SF says to which width.

## R4
Q: After your VMM handles each of these exits, where must the PC point before the next run: an `hvc`, an `smc`, and a data abort it emulated?
A: `hvc`: leave it, the hardware already moved it past the call. `smc`: add 4, it was intercepted before it executed. Data abort: add 4, the saved PC is the faulting instruction (a fault retries), and the VMM has now done its work.

## R5
Q: A guest runs `ldp x0, x1, [x2]` with `x2` pointing into a device window. What is ISV in the syndrome, why, and what does this chapter's VMM do?
A: ISV is 0. The note has room for one register number (SRT) and one size, and a pair load moves two registers, so the hardware cannot describe it. The other syndrome fields are then UNKNOWN, so the VMM stops the VM with a fatal error that prints the instruction word, instead of guessing.

## R6
Q: The guest runs `strb w5, [x1]` to a device, with `x5 = 0x12345678`. What value must reach the device, and which field tells you?
A: `0x78`. SAS is 0, so the access is 1 byte, and the VMM masks the register's value to that size before writing. Sending all of `x5` would let the guest write bytes it never stored.

## R7
Q: Why must `Exit::decode` return a value for every possible 64-bit input instead of panicking on a value it does not expect?
A: The syndrome is the hardware's description of what a possibly hostile guest did. If some value made the decoder panic, the guest could crash the VMM on purpose by producing it. The checkpoint feeds the decoder a million random values to check this.

## R8
Q: Your VMM forgets to advance the PC after an emulated store. What does the exit trace look like, and how does the run end?
A: The same record over and over: same `pc`, same `ipa`, same `value`, only `t_ns` growing, hundreds of thousands per second. The guest retries the store forever, and the run ends only when `--timeout` stops it (exit code 5).

## R9
Q: A guest stops with a fatal error after a long run. Where do you look first to see what led up to it, and what does it hold?
A: The `last exits:` part of the dump: the vCPU's ring of recent exits, oldest first, with the fatal one last. The ring keeps the last 256 exits of each vCPU whether or not `--trace` is on, and the dump prints the last 32.
