# Retrieval 24: macOS guests, the low road: vmapple and AVPBooter (capstone, STRETCH)

## R1
Q: Why is QEMU's vmapple machine a second board in macvmm rather than a few changes to the `virt` map?
A: The two maps conflict. On `virt`, RAM starts at `0x4000_0000`; on vmapple that address is PCI Express configuration space and RAM starts at `0x7000_0000`, with the GIC at `0x1000_0000` and the UART at `0x2001_0000`. Stock Linux and U-Boot expect `virt`, AVPBooter expects vmapple, so each board keeps its own table and neither can move.

## R2
Q: A vmapple run ends by `--timeout` after 20 s. The trace shows 34 MMIO exits in the first 0.5 ms and nothing after them except the cancel, and `--stats` says `exec 19.0 s, wfi 0.000 s`. Is the firmware polling a device, waiting for an interrupt, or neither?
A: Neither. Polling a device we lack would keep producing exits at the same address; waiting for an interrupt would show up as WFI time with low exec time. Here the vCPU executed for almost the whole run without a single exit, so it is running a loop that touches only its ROM and RAM. Why it loops is unknown, and our tracing rules do not let us read the code to find out.

## R3
Q: You change the value returned for unknown reads from 0 to all ones, and the ROM now reaches bdif and asks for a system reset. Has the all-ones machine "fixed" something?
A: No. Both values are guesses about registers we do not implement, and neither is what Virtualization.framework's cfg block holds. The experiment shows that the read value is a variable the ROM depends on; record "with all ones, observed: bdif reached, then PSCI SYSTEM_RESET" in the observed column, not as a fix, and keep the cause in the unknown column.

## R4
Q: The all-ones run printed the same 63 logged accesses eleven times and then `guest fatal: reset storm: more than 10 resets within 10 s`, exit code 3. Explain the sequence.
A: Each boot ended with PSCI `SYSTEM_RESET`. macvmm's default answer to a system reset is to rebuild the machine and boot again, so the ROM ran from its first byte each time and made the same accesses. After more than 10 resets within 10 seconds the guard treats the guest as broken and stops it, so a guest that resets in a loop cannot hold a host core forever.

## R5
Q: Sort into observed, inferred or unknown: "AVPBooter's first device access is a store into the cfg block", "AVPBooter reads disks through bdif", "a later stage loads the kernelcache".
A: The first is observed on our board (the first exit at `pc=0x103478` is a store, and the summary puts the access in the cfg row). The second is inferred: QEMU documents it, and we reached bdif only in the all-ones experiment. The third is unknown: it comes from Apple's description of physical Macs and nothing we ran shows it.

## R6
Q: Why does the vmapple board stop the VM on an ISV=0 access instead of injecting a synchronous external abort, as the `virt` board does?
A: The ISV=0 path must fetch the faulting instruction from guest RAM to decode it, and AVPBooter runs from a ROM that is not guest RAM, so it cannot be decoded. Injecting an abort the ROM would never see under Virtualization.framework would make the rest of the trace a record of our VMM's behaviour, not of the machine the ROM expects. Counting the access and stopping keeps the trace honest.

## R7
Q: `tools/hv-denied-probe/run.sh` prints `hv_vm_create with private ISA 3: HV_DENIED (0xfae94007)`. Is the probe broken, and what would it take to get `HV_SUCCESS`?
A: It is working: `HV_DENIED` is the correct answer on a normally configured Mac. The private CPU mode is reserved for Apple's own helper process, which holds a private `com.apple.private.*` entitlement that an ad-hoc signature cannot carry. Getting past it would mean switching off macOS's system protections, which this project never does or recommends.

## R8
Q: Which parts of your own vmapple work may go into a public repository, and which may not?
A: May: your VMM code, device facts taken from QEMU's public sources (never its code or prose), and counts such as the first exit's PC, how many unknown accesses were logged, which layout rows they fell in and how the run ended. May not: AVPBooter itself or any copy of it, the per-access log lines, the values the ROM wrote, and guesses about what its code does. The rule follows from the licence's sections on boot ROM code (2K) and reverse engineering (2N).
