# Retrieval 21: Firmware: a stricter guest (U-Boot, flash, ISV=0)

## R1
Q: U-Boot's word `0xa9010d22` faults with ISV = 0 and the exit reports IPA `0x12c678`. Which accesses must the VMM perform, at which addresses, and which registers change afterwards?
A: Bits 31:30 are `10` (8-byte elements), mode `10` (plain offset), L = 0 (store), imm7 = 2 (times 8 = 16), Rt2 = 3, Rn = 9, Rt = 2: `stp x2, x3, [x9, #16]`. Two 8-byte stores, `x2` at the exit IPA `0x12c678` and `x3` at `0x12c680` (exit IPA plus the element size). No register changes except the PC, which advances by 4: offset mode has no writeback. In flash, both stores are ignored.

## R2
Q: A guest's `TCR_EL1` says `T0SZ = 25` with 4 KiB pages. How many address bits does a walk resolve, at which levels, and which level-1 entry does the virtual address `0x8008_1828` use?
A: 64 - 25 = 39 bits. A 4 KiB page leaves 12 offset bits, and each level resolves 9 bits, so 27 bits need three levels: 1, 2 and 3. The level-1 index is VA bits 38:30, `0x80081828 >> 30 = 2`.

## R3
Q: Why is our stage-1 walker a loop of at most four table reads instead of "follow table descriptors until you reach a page"?
A: The tables are guest memory, written by the guest, so they are hostile input. A descriptor can point at its own table, or tables can form a cycle; "until a page" would never end, and recursion would exhaust the stack. The architecture never needs more than four levels (0 to 3), so the walk stops after four reads whatever the tables say, and a table outside RAM is a refusal, not a read.

## R4
Q: `ldp x0, x1, [x2]` faults with ISV = 0 at exit IPA `0x0b00_0ff8`, the last 8 bytes of the 4 KiB test device window. What does the VMM do, and what does the guest see?
A: The second element would be at `0x0b00_1000`, outside the test device's window, so the plan is refused before any access: a pair is emulated only inside one device. The VMM injects a synchronous external abort: the guest takes a data abort at its own level (EC `0x25` from EL1), DFSC `0x10`, `FAR_EL1` = the faulting virtual address, `x0` and `x1` unchanged, and the PC not advanced.

## R5
Q: Give the PC, `x0` and what RAM holds at the first instruction for a firmware boot and for a direct Linux boot, with 512 MiB of RAM on our `virt` machine.
A: Firmware boot: `PC = 0x0` (the firmware's first word in flash), `x0 = 0x4000_0000`, and RAM holds only the DTB, at its start. Direct boot: `PC = 0x4020_0000` (the kernel), `x0 = 0x4000_0000`, and RAM holds the DTB, the kernel and the initramfs. Both start at EL1h with interrupts masked (`0x3c5`).

## R6
Q: Why is the firmware ROM kept out of the guest-memory API, and how does the ISV = 0 path still read U-Boot's instructions from it?
A: Everything that writes guest memory on the guest's behalf (virtio devices doing DMA, loaders) goes through that API; keeping the ROM out of it means no guest request can ever change the firmware. The ISV = 0 path gets a separate, read-only hook: when the PC's IPA is not RAM, it asks the ROM for one aligned, bounds-checked 4-byte word.

## R7
Q: At the U-Boot prompt on the reference, you type `mw.l 0x4000000 0xdeadbeef`, then `md.l 0x4000000 1`. What does `md` print, and what appears on standard error?
A: `04000000: 00000000`. The store was a data abort on flash bank 1, answered by the write-ignore flash device, which logs `flash: ignored 4-byte write of 0xdeadbeef at offset 0x0 (flash is read-only, write 1 to this bank)`. The offset is 0 because each bank has its own device.

## R8
Q: The ISV = 0 path has decoded `str x1, [x2]`, and its own walk of `x2` gives an IPA different from the exit's. Why not perform the store at the walked address?
A: The exit's IPA is where the guest really faulted, and the hardware checked permissions only for that access. Our walk reads the tables in memory after the fault, while the hardware used its TLB: another vCPU may have rewritten the instruction or the tables since, or this vCPU may have changed a descriptor without a `TLBI`, so the walk can describe a different page the guest may not even be allowed to touch. The decoded address is only a cross-check: any disagreement is refused with an injected abort.

## R9
Q: The VMM emulates `ldp x3, x4, [x5], #16` on a device. In what order do the accesses and register writes happen, and what if the second read fails?
A: Both reads happen first, on the exit IPA and exit IPA plus 8. Only then are `x3` and `x4` written, then `x5` gets its old value plus 16, then the PC advances by 4. If either read fails, no register changes at all (the reference then applies the unhandled-MMIO policy, by default a fatal stop). For pairs this rarely arises, because the plan already refused any pair not wholly inside one device window.
