# Retrieval 02: An exception, one level up: your first VM exit

## R1
Q: A VM exit reports the syndrome `0x5a00002a`. Which instruction stopped the guest, and what number did it carry?
A: The exception class is `0x5a00002a >> 26 = 0x16`: an `hvc` from 64-bit code. For an `hvc`, the low 16 bits of the syndrome hold its immediate, so the guest ran `hvc #0x2a`.

## R2
Q: An exit shows exception class `0x17` with the guest's PC at `0x40001000`. Before you run the vCPU again, where must the PC point, and why?
A: At `0x40001004`. That class is an `smc`, which the level above intercepts before it executes, so the saved PC still points at the `smc` itself, as for a fault; run it again unchanged and the guest repeats the same call forever.

## R3
Q: An app at EL0 runs `svc #0` at address `0x1000`. Which exception level handles it, and which register holds `0x1004` when the handler starts?
A: EL1, the kernel's level. `ELR_EL1` holds `0x1004`, the preferred return address: a call continues after itself.

## R4
Q: You set the starting PSTATE to `0x3c4` instead of `0x3c5`. What is different about how the guest starts?
A: The low four bits change from `0b0101` to `0b0100`: still EL1, but using the stack pointer of EL0 (`SP_EL0`, "EL1t") instead of EL1's own (`SP_EL1`, "EL1h"). The four DAIF mask bits are still all set.

## R5
Q: A timer interrupt arrives while a guest is in the middle of a loop. Is that a synchronous or an asynchronous exception, and where does the saved return address point?
A: Asynchronous: no instruction caused it. The saved address is the first instruction that had not run yet, so the loop carries on as if nothing happened when the handler returns.

## R6
Q: A guest's first instruction is at `0x40000000`, but your VMM mapped its 16 KiB of RAM at `0x40004000`. What comes back from the first `hv_vcpu_run`?
A: A VM exit for an instruction abort (exception class `0x20`) at PC `0x40000000`: the CPU could not fetch the first instruction, because no stage-2 mapping covers that guest address. Nothing in the guest ran.

## R7
Q: `hv_vm_map` is asked to map 16 KiB of host memory at guest address `0x40002000`. What does it answer on a Mac with the default configuration, and why?
A: An error (`HV_BAD_ARGUMENT`). Mappings come in host pages of 16 KiB, so the guest address, the host address and the size must all be multiples of 16 KiB, and `0x40002000` is not.

## R8
Q: The instruction word `0x14000000` sits after the `hvc` in chapter 02's guest. What does it do, and why is it there?
A: It is `b .`, a branch to itself with offset 0: an endless loop. If the VMM ever resumes the guest past the `hvc`, the vCPU parks there harmlessly instead of running into whatever bytes follow.

## R9
Q: Why does the saved PC point after an `hvc` but at a load that faulted?
A: A call wants to continue after itself once it is answered; a fault must be retried once its cause is fixed, so the faulting instruction runs again.

## R10
Q: Your VMM creates a vCPU on one thread and reads one of its registers with `hv_vcpu_get_reg` from another. What happens, and why?
A: The call fails (the framework answers `HV_BAD_ARGUMENT`), because a vCPU belongs to the thread that created it: the header says its calls "must be called by the owning thread". In our Rust wrapper it does not even compile, because the `Vcpu` type cannot be sent to another thread.
