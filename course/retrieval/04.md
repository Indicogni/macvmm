# Retrieval 04: Guest memory: the only safe access is a copy

## R1
Q: A guest asks the VMM to read 8 bytes at address `0xFFFF_FFFF_FFFF_FFFC`. Guest RAM is `0x4000_0000..0x4400_0000`. Compute `addr + len` in 64-bit wrapping arithmetic, and say whether the check `addr >= 0x4000_0000 && addr + len <= 0x4400_0000` accepts the access.
A: The true sum is `0x1_0000_0000_0000_0004`, which needs 65 bits; wrapped to 64 bits it is `0x4`. Both halves of the check pass (`0xFFFF_FFFF_FFFF_FFFC` is above the base, `0x4` is below the end), so a wrapping check accepts an access that starts 4 bytes below the top of the address space. `checked_add` returns `None` instead, and the access is refused.

## R2
Q: `hv_vm_map` is asked to map 4 KiB of host memory at guest address `0x4000_0000`, which is 16 KiB-aligned. What does it answer on a Mac with the default configuration?
A: `HV_BAD_ARGUMENT`. The address is fine, but the size must be a whole number of 16 KiB host pages, because HVF's stage-2 table, the one that maps guest memory to ours, uses the Mac's 16 KiB page size by default.

## R3
Q: A guest RAM made of two adjacent regions, `0x4000_0000` (64 KiB) and `0x4001_0000` (64 KiB). Is an 8-byte read at `0x4000_FFFC` valid, and why?
A: No. The range crosses from the first region into the second. The two regions are separate host allocations that only look contiguous to the guest, so one copy from a single host pointer would run off the end of the first allocation. An access must lie inside one region.

## R4
Q: Why does the `GuestMemory` contract have no `get_slice` that returns a `&[u8]` into guest RAM?
A: A `&[u8]` promises the compiler that nobody changes those bytes while the reference lives, and the compiler uses that promise (it may load a byte once and reuse the value, or load it twice and assume both loads agree). The guest, another vCPU or a device thread can change guest RAM at any moment, so the promise would be false. The contract hands out copies instead, and the VMM checks its own copy.

## R5
Q: `check_range(GuestAddress(0x4000_0000), 0)` on a valid RAM region: true or false, and why does the contract choose that answer?
A: False. A zero-length range is never a valid access, so `read` and `write` refuse an empty buffer too, and `check_range` is true exactly when the matching `read` would succeed.

## R6
Q: Name two things a volatile load guarantees and two things it does not.
A: It guarantees that the compiler performs the load, at its size, every time the program says so, in program order relative to other volatile accesses, and never assumes the value is unchanged. It does not make an access of several elements atomic, and it gives no ordering or visibility guarantee towards other threads or the guest (that needs atomics and barriers, chapter 16). Volatile does not mean thread-safe.

## R7
Q: `write_u32(GuestAddress(0x4000_0010), 0xdead_beef)` succeeds. Which byte does `read_u8(GuestAddress(0x4000_0010))` return, and why?
A: `0xef`. The helpers are little-endian, like the guest: the least significant byte of the value goes to the lowest address, so the bytes in memory are `ef be ad de`.

## R8
Q: A region table is given the region `base = 0xFFFF_FFFF_FFFF_C000, size = 0x8000`. Both are 16 KiB multiples. Which construction rule rejects it, and what would go wrong without that rule?
A: The overflow rule: `base + size` passes `u64::MAX`. Without it, the region's end would wrap to `0x4000`, and a test of the form `addr < end` would place the region's end in low memory, so the table would answer nonsense for addresses near zero.

## R9
Q: Your VMM's bounds check uses `addr + len` with Rust's default release settings, where overflow is not checked. A guest calls the memory-hash debug call with `addr = 0xFFFF_FFFF_FFFF_FFF0, len = 0x20`. What happens, and what changes if overflow checks are on?
A: Without overflow checks the sum wraps to `0x10`, the range test passes, and the VMM forms a host pointer far outside the RAM allocation: a guest-chosen read of host memory, unless a second check catches it. With overflow checks on, the addition panics, and the guest has crashed the VMM. Both are wrong: only `checked_add`, which turns the overflow into an ordinary error, keeps the VMM running and safe.
