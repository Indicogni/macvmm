# Retrieval 03: A guest of your own, and what an exit costs

## R1
Q: A guest prints `ok` and a newline through DEBUG_PUTC, then powers off. How many records with `"ec":"0x16"` does `--trace exits:t.jsonl:hvc` write, and why?
A: Four. Each printed byte is one `hvc` (three bytes: `o`, `k`, newline), and the power-off call is one more `hvc`. Every one is an exception of class `0x16`.

## R2
Q: Decode the hypercall ID `0xC600_4D02` field by field.
A: Bit 31 = 1, a fast call; bit 30 = 1, the 64-bit convention; bits 29 to 24 = `0x06`, owner 6, vendor-specific hypervisor service; low 16 bits = `0x4D02`, the function. In macvmm that is DEBUG_EXIT, with the exit code in `x1`.

## R3
Q: A guest calls DEBUG_EXIT with `x1 = 3`. What exit status does `macvmm` return to the shell, and what would it return for `x1 = 0`?
A: 6 for any non-zero guest code (and it prints `guest exit code 3`); 0 for code 0. The guest's own number and the monitor's exit status are different things.

## R4
Q: The flat binary of a guest is 11,866 bytes, and its linker map puts `__bss_start` at `0x40082e60` with the image linked at `0x40080000`. After `--raw guest.bin@0x40080000`, what does a zero-initialised static at `0x40082e60` contain before `_start` runs?
A: Whatever that RAM held before: the file ends at offset 11,866 and `0x2e60` is 11,872, so no byte of the file lands there. It reads 0 only if the monitor happened to hand over fresh, zeroed memory; `_start` must zero the BSS itself.

## R5
Q: Your loader checks `addr + len <= ram_end` with a plain `+`. A user passes a 0x2000-byte file at address `0xffff_ffff_ffff_f000`. What goes wrong, and what is the fix?
A: With Rust's default release settings the sum wraps to `0x1000`, which is below the end of RAM, so the check passes and the copy runs off the top of memory (with `overflow-checks` on, as in our workspace, it panics instead: a crash, still not a clean refusal). Use `checked_add` and refuse the file, exit code 2, when it returns `None`.

## R6
Q: `exit-bench` reports 3,600,000 ticks for 100,000 calls on a 24 MHz counter. What is one round trip in nanoseconds?
A: 3,600,000 / 24,000,000 s = 0.15 s; divided by 100,000 that is 1.5 µs, 1,500 ns per round trip.

## R7
Q: Why can a single store instruction not be timed with `CNTVCT_EL0`, and what does `exit-bench`'s method do instead?
A: The counter ticks at 24 MHz, once every 41.7 ns, while a store takes a fraction of a nanosecond, so one store almost never spans a tick. Timing a loop of a million stores and dividing by a million gives the average.

## R8
Q: A guest spins in `b .` and you run it with `--timeout 1`. Why can the vCPU's own thread not notice the timeout, and what exit status do you get?
A: The thread is blocked inside `hv_vcpu_run`, which does not return while the guest runs without exiting, so it cannot look at a clock. Another thread must notice the deadline and stop it (the reference kicks the vCPU; ending the process also works). The exit status is 5.

## R9
Q: After a DEBUG_PUTC exit, your run loop adds 4 to the PC before resuming. What happens to the guest?
A: It skips the instruction after the `hvc`. The hardware already saved the PC past the `hvc` (a call continues after itself), so the extra 4 jumps over code the guest meant to run; an `hvc` exit must resume with the PC unchanged.

## R10
Q: You delete `mov sp, x10` from `_start`. The run prints nothing and the trace's only record is `canceled` at `pc=0x40080a00`, with the guest's vectors at `0x40080800`. Where was the CPU, and why did no exit report the fault?
A: In the guest's own vector entry at `VBAR_EL1 + 0x200`, for an exception taken at EL1 itself. With `sp` = 0, the first stack store used an address no memory could have, so the fault was taken by the guest's own level, not forwarded to EL2; the handler then faulted on the same bad stack, again and again, until the timeout's kick stopped it.
