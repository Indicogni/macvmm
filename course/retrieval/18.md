# Retrieval 18: virtio-blk: a root filesystem that persists

## R1
Q: A virtio-blk request header reads, as little-endian fields, `type = 0`, `reserved = 0`, `sector = 16`, and the chain carries one 4096-byte writable data buffer and a 1-byte writable status. Which bytes of the image file does the device read, and what `len` goes in the used ring when it succeeds?
A: Type 0 is IN (a read). The offset is `16 × 512 = 8192`, so it reads bytes 8192 to 12287 of the file (4096 bytes, eight sectors). The used `len` counts the bytes the device wrote into guest memory: 4096 data bytes plus the status byte, 4097.

## R2
Q: A guest asks to read 512 bytes at `sector = 2^55`. Why can `sector * 512 + len <= capacity` pass in C, and what must the device answer instead?
A: `2^55 × 512 = 2^64`, which wraps to 0 in 64-bit arithmetic, so the check sees offset 0 and passes, and the device would read sector 0, a sector the guest did not ask for. With `checked_mul` and `checked_add` the overflow is an error, and the device answers the status `IOERR` (1) without touching the file. (In Rust with overflow checks on, the plain `*` panics instead: a guest-triggered crash.)

## R3
Q: A request's last descriptor is device-readable, so there is no writable byte anywhere in the chain. Why does the device not answer `IOERR`, and what does it do?
A: The status byte is the last writable byte of the chain; with none, there is nowhere to write any answer, so `IOERR` cannot be delivered. The chain breaks the protocol itself, so the device sets `DEVICE_NEEDS_RESET` (chapter 15) and stops using the queue until the driver resets it. A bad sector number, by contrast, is answered with `IOERR` and the queue carries on.

## R4
Q: The driver accepted `VIRTIO_BLK_F_FLUSH`. A guest `OUT` request completes with status OK. Is the data on the Mac's drive yet, and what makes it so?
A: Not necessarily: with FLUSH negotiated the device is write-back, and an OUT is a `pwrite` into the host's page cache. The data is durable only after a later FLUSH request completes, which our device answers OK only after `File::sync_all`, `fcntl(F_FULLFSYNC)` on macOS, returned success. Without FLUSH negotiated the device must be write-through and sync after every OUT.

## R5
Q: A guest sends request type 11 (a type our device does not implement). What does it answer, and why is that different from the answer for a write to a `,ro` disk?
A: Unknown types get `UNSUPP` (2): "I do not know this request". An OUT on a read-only disk gets `IOERR` (1): the request is understood but cannot be done. Neither resets the device; both are ordinary answers the driver handles. The device also offers `VIRTIO_BLK_F_RO` for a `,ro` disk, so a correct driver never sends the write at all.

## R6
Q: You start a second `macvmm` with `--disk disk.img` while a first one is running on the same file. What happens, and why does a crashed first VMM not leave the file locked forever?
A: The second one prints `disk image is locked` and exits with code 2 before creating a VM: every `--disk` takes an `flock` (exclusive for read-write, shared for `,ro`) on its open file. The lock belongs to the open file, so the kernel releases it when the process's file descriptor closes, which also happens when a process dies. It is advisory: a program that never calls `flock` is not stopped.

## R7
Q: Your VMM answers FLUSH by doing nothing. You `kill -9` it right after the guest's `dd ... conv=fsync` returns. Are the guest's bytes in the image file?
A: Yes. The device already handed them to macOS with `pwrite`; they sit in the host's page cache, which belongs to the kernel, not to our process, so killing the process loses nothing. Only a power cut or a kernel crash before the drive wrote them shows the difference. That is why the no-op FLUSH passes every test: the experiment shows latency, not corruption.

## R8
Q: `GET_ID` arrives with a 64-byte writable data buffer. How many bytes does our device write there, and what are they?
A: Twenty at most (the virtio-blk ID is 20 bytes): `macvmm-disk0` for the first `--disk`, padded with zero bytes. It writes `min(20, buffer length)` bytes, and the used `len` is those bytes plus 1 for the status. Linux shows the string in `/sys/block/vda/serial`.
