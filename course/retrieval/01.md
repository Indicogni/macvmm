# Retrieval 01: Where our VMM sits: Hypervisor.framework and a hand-written FFI

## R1
Q: Your doctor prints `hv_vm_create: HV_BUSY (0xfae94002)`. What is the most likely cause in your own code?
A: A VM already exists in this process: Hypervisor.framework allows one per process. Usually an earlier `Vm` is still alive, or was dropped without `Drop` calling `hv_vm_destroy`.

## R2
Q: `hv_vm_create` returns `0xfae94009`, a code your `HvError` does not list. What should `HvError::from_code` return, and why not a generic "unknown error"?
A: `HvError::Unknown(0xfae94009)`. The exact value is the evidence a bug report needs, and a newer macOS may add codes; `Display` still prints it in full.

## R3
Q: A freshly built `macvmm`, run without the signing runner, gets `HV_DENIED (0xfae94007)`. Is that a link problem? What fixes it?
A: No: the program linked and started; the kernel refused at the call because the signature has no `com.apple.security.hypervisor`. Run it through `cargo run` (the runner signs a copy first) or sign it with `scripts/sign.sh`.

## R4
Q: A guest stores a byte to `0x0900_0000`, where nothing is mapped. Which layer decides that this access leaves the guest, and which decides what it means?
A: The macOS kernel's EL2 part decides it stops the guest and forwards it (a VM exit); our VMM, an ordinary EL0 process, decides what it means, by playing the device at that address.

## R5
Q: Inside an `unsafe` block you index a slice out of bounds. What happens, and what does that tell you about `unsafe`?
A: It still panics: bounds checks on safe indexing stay on, as do type and borrow checks. `unsafe` only allows a few extra operations (such as calling an FFI function); the invariants those operations need become yours.

## R6
Q: The header declares `hv_return_t hv_vm_get_max_vcpu_count(uint32_t *max_vcpu_count);`. What is the Rust parameter type, and who owns the memory it points to?
A: `*mut u32`. It is an out-pointer: the caller owns a live, writable `u32` (for example a local variable) and passes its address; the function writes the answer there and returns only an error code.

## R7
Q: Why does `hv_vm_destroy` take no argument at all?
A: There is no handle to pass: the VM belongs to the whole process, and there can be only one, so "destroy the VM" is unambiguous.

## R8
Q: At which exception level does `macvmm` itself run, and at which does the guest kernel run?
A: `macvmm` runs at EL0, like any app. The guest kernel runs natively at EL1. The level above both, EL2, belongs to part of the macOS kernel.

## R9
Q: A guest reads the clock counter with `mrs x0, CNTVCT_EL0` a million times. How many of those reads reach our VMM?
A: None: the hardware virtualizes the counter, so the read completes inside the guest without any exit.
