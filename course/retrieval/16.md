# Retrieval 16: Split virtqueues: shared memory with an adversary

## R1
Q: A queue of size 8 last served up to `next_avail = 0xFFFE`. The device now loads `avail.idx = 0x0002`. How many new requests are there, and in which ring slots are their heads?
A: Four: `0x0002 - 0xFFFE` in wrapping `u16` arithmetic is 4 (`0x10002 - 0xFFFE`). The slots are the indices modulo 8: `0xFFFE & 7 = 6`, then 7, 0 and 1. Nothing special happens at the wrap, because the indices are free-running counters and only the slot is reduced modulo the size.

## R2
Q: Same queue, `next_avail = 0`, and the device loads `avail.idx = 9`. What does it do, and why is "serve 9 requests" wrong?
A: It refuses: the queue is marked broken and the transport sets `DEVICE_NEEDS_RESET`. Only 8 slots exist, so an honest driver can never be more than 8 requests ahead; a jump of 9 (or 65535) is a broken or hostile driver, and looping over it would re-serve stale slots or burn time the guest chose.

## R3
Q: The driver places a size-256 used ring at `0x4000_5002`. Which check refuses it, and how many bytes would the ring have needed?
A: The alignment check: the used ring must be 4-byte aligned, and `0x...02` is not. Had it been aligned, the ring needs `6 + 8 × 256 = 2054` bytes (flags, idx, 256 elements of `{id, len}`, and `avail_event`), all inside one RAM region, computed with `checked_mul` and `checked_add`.

## R4
Q: Descriptor 0 of a size-8 queue is `{addr: 0x0900_0000, len: 8, flags: 0, next: 0}`. Every number fits its field. Why does our walker refuse it, and what would a device that accepted it do?
A: `0x0900_0000` is the PL011's MMIO window, not RAM, so `check_range` fails and the walker returns `BufferOutOfRam`. A device that accepted it would read or write its "buffer" through whatever lives at that address: a guest could aim the device's own memory accesses at device registers or firmware, the bug class our copy-only, RAM-only memory API exists to rule out.

## R5
Q: A chain is `[0: writable, NEXT → 1]`, `[1: readable]`. Each descriptor passes its own checks. What does `into_validated` return, and why does the order matter?
A: `ReadableAfterWritable`. The spec has the driver put every device-readable buffer before every device-writable one, so a device can read the whole request before it writes any reply. A device that accepted the mixed order would have to guess which part is the header and which the reply, and a naive one writes its reply into a buffer the guest meant only to be read.

## R6
Q: Why can a walker stop a self-looping chain by counting hops instead of remembering which descriptors it visited, and what is the limit?
A: A legal chain uses each descriptor at most once, so it can never be longer than the table: N hops for a queue of size N, or `len / 16` inside an indirect table. A walk that wants hop N + 1 must have revisited something, which is a loop or a chain no driver may build. A counter needs no allocation whose size the guest chooses.

## R7
Q: A device validates `desc.len`, then later reads `desc.len` from guest memory again to decide how much to copy. Name the bug and the fix.
A: A double fetch, the TOCTOU (time of check to time of use) bug: another guest vCPU can change `len` between the check and the use, so the device uses a length it never checked. The fix is to copy the whole descriptor once with `read_obj`, validate the copy, and use only the copy.

## R8
Q: Which two guest-memory accesses of the split ring are ordered, and what does each one order?
A: The acquire load of `avail.idx`, which keeps every later read (ring entries, descriptors, buffers) after it, so we see what the driver wrote before it published the index; and the release store of `used.idx`, which keeps every earlier write (the used element and the buffer data) before it. Everything else is a plain copy. A full `SeqCst` fence also sits between our `used.idx` store and our load of `avail.flags`.

## R9
Q: The device wrote 150 bytes into a request whose writable buffers total 200. What goes in the used element's `len`, and what goes wrong if you put 200?
A: 150, the bytes actually written. The driver trusts `len`: with 200 it would treat 50 bytes the device never wrote, whatever was in that memory before, as data, for example as random numbers or as file contents.
